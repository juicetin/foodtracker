# Phase 3.2: Food Search + Manual Add + Quick Add - Research

**Researched:** 2026-03-21
**Domain:** React Native search UI, SQLite full-text search, food diary integration
**Confidence:** HIGH

## Summary

This phase extends the existing FoodSearchScreen with history-based ranking, adds a Quick Add escape hatch for raw macro entry, and integrates a persistent search bar into DiaryScreen. The codebase already has a working search screen (`FoodSearchScreen.tsx`) that queries both the Knowledge Graph (FTS5 + SymSpell) and Open Food Facts (with SQLite cache). The primary work is: (1) adding a history query layer that ranks by frequency + recency, (2) building a QuickAdd screen with macro validation, and (3) wiring a search bar into DiaryScreen that navigates to FoodSearchScreen.

The existing infrastructure is mature -- Drizzle ORM schema, food_entries table with notes field, OFF cache with stale-while-revalidate, KG with FTS5 search, and searchDedup service. No new libraries are needed. All work is pure React Native + SQLite.

**Primary recommendation:** Enhance the existing FoodSearchScreen with a history section (queried from food_entries), add a QuickAdd modal/screen for raw calorie+macro entry, and embed a search bar in DiaryScreen header that navigates to FoodSearchScreen.

### Pattern 1: History Query via Raw SQL
**What:** Query food_entries for logged food history, ranked by frequency and recency
**When to use:** When the user opens FoodSearchScreen before typing anything, or when history results should appear alongside search results
**Example:**
```typescript
// Query food history -- frequency + recency blend
// Uses the notes field which contains food name (e.g. "Chicken Breast (150g)")
// Also queries scanned_dishes.name for camera-logged meals
const SQL_HISTORY_BY_FREQUENCY = `
  SELECT name, SUM(count) as total_count, MAX(last_logged) as last_logged,
         AVG(calories) as avg_calories, AVG(protein) as avg_protein,
         AVG(carbs) as avg_carbs, AVG(fat) as avg_fat
  FROM (
    -- From scanned dishes
    SELECT sd.name, COUNT(*) as count, MAX(fe.created_at) as last_logged,
           fe.total_calories / NULLIF(
             (SELECT COUNT(*) FROM scanned_dishes sd2 WHERE sd2.entry_id = fe.id), 0
           ) as calories,
           fe.total_protein / NULLIF(
             (SELECT COUNT(*) FROM scanned_dishes sd2 WHERE sd2.entry_id = fe.id), 0
           ) as protein,
           fe.total_carbs / NULLIF(
             (SELECT COUNT(*) FROM scanned_dishes sd2 WHERE sd2.entry_id = fe.id), 0
           ) as carbs,
           fe.total_fat / NULLIF(
             (SELECT COUNT(*) FROM scanned_dishes sd2 WHERE sd2.entry_id = fe.id), 0
           ) as fat
    FROM scanned_dishes sd
    JOIN food_entries fe ON sd.entry_id = fe.id
    WHERE fe.is_deleted = 0
    GROUP BY sd.name

    UNION ALL

    -- From manual/quick-add entries (notes field contains the food name)
    SELECT fe.notes as name, COUNT(*) as count, MAX(fe.created_at) as last_logged,
           fe.total_calories as calories, fe.total_protein as protein,
           fe.total_carbs as carbs, fe.total_fat as fat
    FROM food_entries fe
    WHERE fe.is_deleted = 0 AND fe.notes IS NOT NULL AND fe.notes != ''
      AND fe.id NOT IN (SELECT entry_id FROM scanned_dishes)
    GROUP BY fe.notes
  )
  GROUP BY name
  ORDER BY total_count DESC, last_logged DESC
  LIMIT ?
`;
```

### Pattern 2: Macro Validation Formula
**What:** Real-time validation of calorie/macro consistency
**When to use:** In QuickAdd form as user enters values
**Example:**
```typescript
function validateMacros(cal: number, protein: number, carbs: number, fat: number): {
  isValid: boolean;
  expected: number;
} {
  const expected = protein * 4 + carbs * 4 + fat * 9;
  // Allow rounding tolerance: within 10% or 20 kcal, whichever is greater
  const tolerance = Math.max(expected * 0.1, 20);
  return {
    isValid: Math.abs(cal - expected) <= tolerance,
    expected: Math.round(expected),
  };
}
```

### Anti-Patterns to Avoid
- **Fetching all history on mount:** Use LIMIT and pagination. History could be thousands of entries.
- **Separate state stores for search:** Keep search state local to FoodSearchScreen (useState). No need for Zustand store -- search is ephemeral.
- **Complex serving size picker:** A simple TextInput for grams (already built) is sufficient. Fancy pickers add friction.
- **Blocking on OFF network requests:** OFF search should not block rendering. Show KG + history results first, append OFF results when they arrive.

## Common Pitfalls

### Pitfall 1: History Query Performance
**What goes wrong:** Querying all food_entries + scanned_dishes + GROUP BY on every keystroke
**Why it happens:** History needs aggregate data (frequency, recency) which requires scanning many rows
**How to avoid:** Load history ONCE on screen mount (or when empty query), cache in component state. Only re-query KG+OFF on text input.
**Warning signs:** Search feels sluggish on first character typed

### Pitfall 2: Notes Field Parsing for History
**What goes wrong:** The `notes` field in food_entries contains freeform text like "Chicken Breast (150g)" or "Copied: carbonara, salad" or "Barcode: 123... | Product Name (100g)"
**Why it happens:** Different entry paths format notes differently
**How to avoid:** For history, prefer scanned_dishes.name (clean dish names). For manual entries, parse the food name out of notes. For Quick Add, store a structured source field or use a consistent notes format.
**Warning signs:** History shows raw notes strings like "Copied: ..." or "Barcode: ..."

### Pitfall 3: QuickAdd Validation UX
**What goes wrong:** User enters calories first, validation shows red immediately before they enter macros
**Why it happens:** Validation fires on every field change
**How to avoid:** Only show validation warning when ALL four fields have non-zero values. If only Cal is filled, don't validate yet.
**Warning signs:** Red borders appearing while user is still filling in the form

### Pitfall 4: Barcode Icon Tap Does Nothing
**What goes wrong:** User taps barcode icon, nothing happens, feels broken
**Why it happens:** Stub with no feedback per user decision
**How to avoid:** Per CONTEXT.md decision: no-op, no toast, no stub screen. Just do nothing. This is intentional -- the icon is a placeholder for future wiring.
**Warning signs:** N/A -- this is the intended behavior

### Pitfall 5: Navigation State After Adding Food
**What goes wrong:** After adding food from search, user is stuck on detail view
**Why it happens:** Alert.alert callback doesn't navigate back to diary
**How to avoid:** After successful add, navigate back to diary (goBack or popToTop). Current code clears state but stays on search -- should offer "Add another" vs "Done" flow.
**Warning signs:** User has to manually press back after every food add

   - What's unclear: Whether QuickAdd should be a full screen or inline on FoodSearchScreen

2. **QuickAdd route in navigation?**
   - What we know: RootStackParamList needs a `QuickAdd` entry
   - What's unclear: Whether it's better to add a new route or reuse FoodSearch with a mode param
   - Recommendation: New route `QuickAdd: undefined` -- cleaner separation, simpler navigation

3. **Notes field vs structured source tracking**
   - What we know: Currently notes is freeform text with different formats per source
   - What's unclear: Whether to add a `source` column to food_entries for cleaner history
   - Recommendation: Defer schema migration. Use consistent notes prefix (`"Quick Add: "`, `"Search: "`) and parse scanned_dishes.name for camera entries. A source column is a future improvement.
