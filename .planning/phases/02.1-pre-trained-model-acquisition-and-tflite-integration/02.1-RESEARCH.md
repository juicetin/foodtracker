# Phase 02.1: Pre-trained Model Acquisition and TFLite Integration - Research

**Researched:** 2026-03-13
**Domain:** TFLite model acquisition, bundling, and pipeline integration for React Native
**Confidence:** HIGH

## Summary

This phase closes the critical gap discovered during Phase 2 verification: the entire three-stage detection pipeline exists in code but has zero actual ML models to run. The pipeline throws "model pack not installed" and nothing can be tested on-device. Two pre-trained models are needed: Google AIY Food V1 (MobileNet V1, 2023 food classes, ~6MB, Apache 2.0) for both binary gate and classification stages, and YOLO26n COCO-pretrained (~8-12MB) for detection with bounding boxes.

The existing infrastructure is well-prepared. Metro bundler already recognizes `.tflite` files. The `react-native-fast-tflite ^2.0.0` library is installed with its Expo plugin configured (CoreML + GPU delegates). The PackManager system, installed_packs table, and modelLoader all exist and work. The primary work is: (1) acquire the two models, (2) adapt the binary gate output interpretation since AIY Food V1 outputs 2023-class probabilities rather than a single binary score, (3) create a model manifest compatible with PackManager, (4) bundle the models for initial testing, and (5) build a testable APK.

**Primary recommendation:** Use a two-script approach: a Python acquisition script (`training/acquire_pretrained.py`) to download AIY Food V1 and export YOLO26n to TFLite, plus TypeScript-side changes to adapt the binary gate interpretation and create a model bootstrap function that registers bundled models with PackManager on first launch.

### Pattern 1: Bundled Model Registration on First Launch
**What:** On app first launch (or when models are not in installed_packs), a bootstrap function copies bundled assets to the packs directory and registers them in installed_packs table.
**When to use:** For the v1 build where models ship with the APK.
**Why:** The existing modelLoader.ts queries installed_packs for file paths. Bundled `require()` assets use a different loading path. Rather than rewriting modelLoader, we register the bundled models as "installed" packs on first launch.

```typescript
// Pattern: Bootstrap bundled models into PackManager system
import { Paths, File, Directory } from 'expo-file-system';
import { userDb } from '../db/client';
import { installedPacks } from '../db/schema';
import { eq } from 'drizzle-orm';

// Model manifest embedded as JSON
import manifest from '../../assets/models/model_manifest.json';

export async function bootstrapBundledModels(): Promise<void> {
  for (const model of manifest.models) {
    // Check if already registered
    const existing = await userDb
      .select()
      .from(installedPacks)
      .where(eq(installedPacks.id, model.id));
    if (existing.length > 0) continue;

    // Copy bundled asset to packs directory
    const packDir = `${Paths.document.uri}packs/model/${model.id}/`;
    const dir = new Directory(packDir);
    if (!dir.exists) dir.create();

    // For bundled models, the require() path resolves at build time
    // We need to copy from the bundled asset location to the packs dir
    const destPath = `${packDir}${model.file}`;
    // ... copy logic using expo-file-system

    // Register in installed_packs
    await userDb.insert(installedPacks).values({
      id: model.id,
      name: model.name,
      type: 'model',
      version: model.version,
      filePath: destPath,
      sizeBytes: model.sizeBytes,
      sha256: null, // Bundled models skip hash verification
      region: null,
      installedAt: new Date().toISOString(),
      lastChecked: new Date().toISOString(),
    });
  }
}
```

### Pattern 2: Alternative -- Direct require() Loading Path
**What:** Add a `require()`-based fallback to modelLoader.ts that loads bundled assets directly when installed_packs has no entries.
**When to use:** Simpler approach that avoids the file copy step.
**Trade-off:** Diverges from the PackManager pattern and requires modifying modelLoader.

```typescript
// Alternative: Direct bundled asset loading fallback
const BUNDLED_BINARY = require('../../../assets/models/binary.tflite');
const BUNDLED_DETECT = require('../../../assets/models/detect.tflite');
const BUNDLED_CLASSIFY = require('../../../assets/models/classify.tflite');

async function loadBundledFallback(): Promise<ModelSet> {
  const [binary, detect, classify] = await Promise.all([
    loadTensorflowModel(BUNDLED_BINARY, 'default'),
    loadTensorflowModel(BUNDLED_DETECT, 'default'),
    loadTensorflowModel(BUNDLED_CLASSIFY, 'default'),
  ]);
  return { binary, detect, classify } as unknown as ModelSet;
}
```

**Recommendation:** Use Pattern 2 (direct `require()` loading) as the primary path for bundled models. It is simpler, avoids file copy complexity, and `require()` is the recommended loading method for react-native-fast-tflite. Add the fallback to modelLoader.ts -- try installed_packs first (for future R2-downloaded models), then fall back to bundled assets.

### Pattern 3: Binary Gate Adaptation for AIY Food V1
**What:** The existing inferenceRouter.ts reads `output[0]` as a binary score. The AIY Food V1 model outputs 2023 class probabilities. The binary gate interpretation must take the MAX probability across all classes as the "food confidence" score.
**When to use:** Critical -- without this adaptation, the binary gate always reads the first class probability (which may be low) and short-circuits to "not food".

```typescript
// CURRENT (broken with AIY model):
const binaryScore = new Float32Array(binaryOutput[0] as ArrayBuffer)[0];

// NEEDED (works with AIY model):
const binaryScores = new Float32Array(binaryOutput[0] as ArrayBuffer);
const binaryScore = Math.max(...binaryScores);
// Alternative for performance (avoid spread on 2023-element array):
let binaryScore = 0;
for (let i = 0; i < binaryScores.length; i++) {
  if (binaryScores[i] > binaryScore) binaryScore = binaryScores[i];
}
```

### Pattern 4: COCO Food Class Filtering
**What:** YOLO26n COCO has 80 classes but only 10 are food. The postProcess/NMS step already filters by classNames array, but the class IDs need to map correctly.
**When to use:** When wiring YOLO26n COCO output to the detection pipeline.

```typescript
// COCO food classes with their IDs (0-indexed in YOLO output)
```

**Note:** The detection pipeline's postProcess.ts decodes ALL 80 COCO classes. The classNames array passed to `runDetectionPipeline()` must have all 80 COCO class names at correct indices. The `DEFAULT_CLASS_NAMES` in DetectionScreen.tsx (currently 20 custom food names) must be replaced with the full COCO 80-class array, and optionally post-filter to only show food classes.

### Anti-Patterns to Avoid
- **Using GPU delegate for YOLO26n TFLite on Android:** Known issue (#23282) -- INT64 tensor type operations are unsupported. Use `'default'` (CPU) delegate. The existing code already uses `'default'`, so no change needed.
- **Using `Math.max(...array)` on large arrays:** For the 2023-element AIY output, `Math.max(...binaryScores)` risks stack overflow on some engines. Use a manual loop instead.
- **Baking NMS into TFLite export:** The existing decision (ADR, export_mobile.py) is `nms=False` because react-native-fast-tflite's LiteRT runtime doesn't support YOLO's built-in TFLite NMS op. NMS is done in JavaScript.
- **Expecting the same model to serve as both binary gate and classifier with the same input size:** Both stages use the AIY Food V1 model, and both use 224x224 input. However, the binary gate runs on the full image while the classifier should ideally run on each detected crop. For v1, running the classifier on the full image is acceptable (the YOLO detection already provides class labels from COCO).

## Common Pitfalls

### Pitfall 1: Binary Gate Misinterpretation
**What goes wrong:** AIY Food V1 outputs 2023 class probabilities, not a single binary score. Taking `output[0]` gives the probability of the first food class (e.g., "Baked Alaska"), which is almost always near-zero.
**Why it happens:** The original pipeline was designed for a dedicated binary classifier with 2 output classes (food/not-food).
**How to avoid:** Take the MAX across all 2023 output probabilities. If max > BINARY_THRESHOLD, it's food.
**Warning signs:** Pipeline always short-circuits to "not food" regardless of input image.

### Pitfall 2: YOLO26n TFLite GPU Delegate Crash on Android
**What goes wrong:** Using `'android-gpu'` delegate with YOLO26n TFLite causes unsupported operator errors (INT64 CAST, ADD v4, MUL v5).
**Why it happens:** YOLO26 architecture uses operations not yet supported by LiteRT 2.1.0 GPU delegate.
**How to avoid:** Use `'default'` delegate (CPU). The existing modelLoader.ts already does this.
**Warning signs:** App crash on model load with "Expected one of these TensorType: [12]" errors.

### Pitfall 3: COCO Class Index Mismatch
**What goes wrong:** Passing only food class names (10 items) to postProcess.ts but the model outputs 80 COCO classes. classId 46 (banana) maps to `classNames[46]` which is undefined.
**Why it happens:** DetectionScreen currently passes a 20-element `DEFAULT_CLASS_NAMES` array.
**How to avoid:** Pass the complete 80-class COCO names array. Post-filter detections to only include food classes.
**Warning signs:** All detected items show as "class_46", "class_53", etc.

### Pitfall 4: Input Size Mismatch Between Models
**What goes wrong:** AIY Food V1 expects 224x224 input, YOLO26n expects 640x640. The current pipeline sends the same buffer to all three stages.
**Why it happens:** DetectionScreen preprocesses to 640x640 (line 199) and passes the same buffer to the entire pipeline.
**How to avoid:** Preprocess the image at both sizes. Binary gate and classify get 224x224; detect gets 640x640. Alternatively, resize in the inference router before each stage.
**Warning signs:** Binary gate produces garbage outputs (stretched/squished input tensor), or model inference crashes due to buffer size mismatch.

### Pitfall 5: AIY Food V1 Input Normalization
**What goes wrong:** The model may expect uint8 [0-255] or float32 [-1, 1] rather than float32 [0, 1] as the current imagePreprocess.ts produces.
**Why it happens:** MobileNet V1 models have varying normalization conventions. The original Google AIY model was likely trained with [-1, 1] normalization (standard for MobileNet) rather than [0, 1].
**How to avoid:** Inspect the model's input tensor details using Python `tflite_runtime.Interpreter.get_input_details()` to determine the expected dtype and quantization parameters. Adapt preprocessing accordingly.
**Warning signs:** All outputs are near-uniform probability (model sees noise instead of an image).

### Pitfall 6: Model File Size and APK Bloat
**What goes wrong:** Bundling ~20MB of models increases APK size and potentially hurts conversion rates.
**Why it happens:** Research from STATE.md notes: "Base APK must stay under 100MB (6MB = ~1% conversion drop)".
**How to avoid:** FP16 YOLO26n should be ~8-12MB. AIY Food V1 is ~6MB but used for two stages (binary + classify), so only one copy needed. Total ~18-20MB increase. This is acceptable for the v1 testing build; production will use on-demand delivery (Phase 6, MDL-01).
**Warning signs:** APK exceeds 100MB limit.

```python
AIY_FOOD_URL = "https://storage.googleapis.com/tfhub-lite-models/google/lite-model/aiy/vision/classifier/food_V1/1.tflite"

def download_aiy_food(output_dir: str) -> str:

    os.makedirs(output_dir, exist_ok=True)
```

### Validating Model I/O Shapes (Python)
```python
# Source: TensorFlow Lite Python API
import numpy as np

def validate_model(model_path: str) -> dict:
    """Inspect and validate a TFLite model's I/O shapes."""
    try:
        import tflite_runtime.interpreter as tflite
    except ImportError:
        import tensorflow.lite as tflite

    interpreter = tflite.Interpreter(model_path=model_path)
    interpreter.allocate_tensors()

    input_details = interpreter.get_input_details()
    output_details = interpreter.get_output_details()

    # Run dummy inference
    input_shape = input_details[0]["shape"]
    dummy = np.zeros(input_shape, dtype=input_details[0]["dtype"])
    interpreter.set_tensor(input_details[0]["index"], dummy)
    interpreter.invoke()
    output = interpreter.get_tensor(output_details[0]["index"])

    return {
        "input_shape": input_shape.tolist(),
        "input_dtype": str(input_details[0]["dtype"]),
        "output_shape": output.shape,
        "output_dtype": str(output_details[0]["dtype"]),
    }
    # Expected for AIY Food V1:
    #   input_shape: [1, 224, 224, 3], dtype: uint8 or float32
    #   output_shape: [1, 2023], dtype: float32
    #
    # Expected for YOLO26n COCO (FP16):
    #   input_shape: [1, 640, 640, 3], dtype: float32
    #   output_shape: [1, 84, 8400], dtype: float32
    #   (84 = 4 bbox coords + 80 COCO classes, 8400 predictions)
```

## Open Questions

1. **AIY Food V1 Input Normalization**
   - What we know: MobileNet V1 typically uses [-1, 1] normalization, but some TFLite versions use uint8 [0, 255] input.
   - What's unclear: Whether the specific AIY Food V1 TFLite file expects float32 [0, 1], float32 [-1, 1], or uint8 [0, 255].
   - Recommendation: The acquisition script MUST inspect the model's `get_input_details()` to determine dtype and quantization params, then document the finding. The TypeScript preprocessing may need adjustment (currently normalizes to [0, 1]).
   - Confidence: MEDIUM -- resolvable during implementation by model inspection.

2. **AIY Food V1 Label File**
   - What we know: The model has 2023 output classes. Labels may be embedded in the TFLite file as metadata (zip-extractable) or available separately.
   - What's unclear: Exact format and availability of the label file.
   - Recommendation: Try extracting metadata from the .tflite file using `zipfile` module (TFLite models with metadata are zip files). If not embedded, search for `aiy_food_V1_labelmap.csv` in Kaggle/TFHub datasets. If unavailable, the labels are not critical for v1 (classification uses YOLO COCO labels primarily; the AIY model's max-confidence approach for binary gate doesn't need label names).
   - Confidence: MEDIUM -- labels needed for classify stage but can use index-based fallback.

3. **YOLO26n TFLite Output Shape Verification**
   - What we know: Expected output shape is [1, 84, 8400] for 80 COCO classes + 4 bbox coords at 640x640 input. The existing postProcess.ts uses transposed access.
   - What's unclear: Whether FP16 export changes the output shape or data layout compared to float32.
   - Recommendation: Validation script must verify output shape after export.
   - Confidence: HIGH -- the existing export_mobile.py has the right patterns.

4. **Dual Input Size for Pipeline**
   - What we know: Binary gate and classify need 224x224, detect needs 640x640. Current pipeline preprocesses once at 640x640.
   - What's unclear: Best approach to handle two input sizes.
   - Recommendation: Preprocess at both sizes in the pipeline entry point. Cache both buffers. Pass the correct one to each stage. Alternatively, the binary stage could accept 640x640 input (just pad/resize in the model -- but AIY is fixed at 224x224).
   - Confidence: HIGH -- this is a known code change needed.
