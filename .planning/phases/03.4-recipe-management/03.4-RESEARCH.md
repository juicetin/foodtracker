# Phase 03.4: Recipe Management - Research

**Researched:** 2026-03-21
**Domain:** React Native UI + SQLite CRUD (recipe management, search integration, Gemini Nano prompt extension)
**Confidence:** HIGH

## Summary

Phase 03.4 builds recipe management features on top of a mature codebase with extensive existing infrastructure. The `custom_recipes`, `recipe_ingredients`, and `recipe_photos` tables already exist in the Drizzle schema. A fully functional `recipeService.ts` provides CRUD operations and `logRecipeAsEntry()`. The existing `RecipeScreen.tsx` has a list view and builder view with URL import. The `EntryDetailScreen.tsx` already has a "Save to Favourites" button pattern that can be adapted for "Save as Recipe."

The primary work is: (1) adding a "Save as Recipe" action on EntryDetailScreen that copies dishes/ingredients into custom_recipes, (2) enhancing RecipeScreen with photo, per-serving macros, usage frequency, search, and edit-with-versioning, (3) integrating recipe results into FoodSearchScreen, (4) updating the Gemini Nano prompt to suggest a recipe name, and (5) implementing the "Update all" vs "Save as new" versioning flow for recipe edits.

**Primary recommendation:** Extend the existing recipeService.ts with `saveEntryAsRecipe()` and `searchRecipes()` functions, enhance RecipeScreen UI, add a recipe source badge to FoodSearchScreen, and update the Gemini Nano prompt to include recipe name suggestion.

### Pattern 1: Save Entry as Recipe (EntryDetailScreen -> recipeService)
**What:** Copy a food entry's dishes and ingredients into custom_recipes + recipe_ingredients tables, link the entry's photo(s) to recipe_photos.
**When to use:** User taps "Save as Recipe" on EntryDetailScreen.
**Example:**
```typescript
// In recipeService.ts
export function saveEntryAsRecipe(
  entryId: string,
  recipeName: string,
  servingCount?: number,
): string {
  const id = generateId();
  const now = new Date().toISOString();

  // Load entry dishes + ingredients
  const dishes = opsqlite.executeSync(
    'SELECT id, name FROM scanned_dishes WHERE entry_id = ?',
    [entryId],
  ).rows;

  // Create recipe with sourceEntryId link
  opsqlite.executeSync(
    `INSERT INTO custom_recipes (id, name, source_entry_id, created_at, updated_at)
     VALUES (?, ?, ?, ?, ?)`,
    [id, recipeName, entryId, now, now],
  );

  // Copy ingredients from all dishes
  for (const dish of dishes) {
    const ings = opsqlite.executeSync(
      'SELECT name, quantity, unit, calories, protein, carbs, fat FROM ingredients WHERE dish_id = ?',
      [dish.id],
    ).rows;
    for (const ing of ings) {
      addRecipeIngredient({ recipeId: id, ...ing });
    }
  }

  // Copy photos to recipe_photos
  const photos = opsqlite.executeSync(
    'SELECT uri, local_path FROM photos WHERE entry_id = ?',
    [entryId],
  ).rows;
  // First photo is primary
  for (let i = 0; i < photos.length; i++) {
    opsqlite.executeSync(
      `INSERT INTO recipe_photos (id, recipe_id, local_path, is_primary, created_at)
       VALUES (?, ?, ?, ?, ?)`,
      [generateId(), id, photos[i].local_path ?? photos[i].uri, i === 0 ? 1 : 0, now],
    );
  }

  recalculateRecipeTotals(id);
  return id;
}
```

### Pattern 3: Recipe Search Integration in FoodSearchScreen
**What:** Add recipe results alongside KG and OFF results in food search.
**When to use:** Always -- recipe results appear at top of search results.
**Example:**

```typescript
// In recipeService.ts
export function searchRecipes(query: string, limit: number = 10): RecipeSummary[] {
  const rows = opsqlite.executeSync(
    `SELECT * FROM custom_recipes
     WHERE name LIKE ? COLLATE NOCASE
     ORDER BY times_used DESC, last_used_at DESC NULLS LAST
     LIMIT ?`,
    [`%${query}%`, limit],
  ).rows;
  return rows.map(mapRecipeRow);
}
```

### Anti-Patterns to Avoid
- **Storing recipe data in Zustand global state:** The recipe list is screen-local. Use useState + recipeService calls. Only diary entries need global Zustand state.
- **Deep-copying all entry data into recipe:** Only copy ingredients and photos. Don't copy bounding boxes, AI confidence, or detection metadata into recipes.
- **Rebuilding RecipeScreen from scratch:** The existing screen works. Enhance it incrementally (add photo display, per-serving macros, search bar, edit versioning).

## Common Pitfalls

### Pitfall 1: Recipe-Entry Linkage for "Update All"
**What goes wrong:** No reliable way to find diary entries created from a specific recipe.
**Why it happens:** Current `logRecipeAsEntry()` stores `notes: "Recipe: ${recipe.name}"` -- string matching is fragile if recipe is renamed.
**How to avoid:** Add a `source_recipe_id` column to `food_entries` (or use the existing `notes` field with recipe ID, not name). Alternatively, create a `recipe_entry_links` join table.
**Warning signs:** "Update all" misses entries or updates wrong ones.
**Recommendation:** Add `source_recipe_id TEXT` column to food_entries via migration. This is the cleanest approach and enables reliable lookback.

### Pitfall 2: Serving Size Math
**What goes wrong:** Confusion between "per recipe" and "per serving" nutrition values.
**Why it happens:** custom_recipes stores total nutrition for the entire recipe; user wants to see per-serving values.
**How to avoid:** Add a `servings` column to custom_recipes (default 1). Display: totalCalories / servings. When re-logging, prompt for serving count and scale accordingly.
**Warning signs:** User logs 1 serving but gets the full recipe's calories.

### Pitfall 3: Photo Path Validity
**What goes wrong:** Recipe photo shows broken image after app update or file cleanup.
**Why it happens:** recipe_photos.local_path may point to a moved or deleted file.
**How to avoid:** Use the same URI/path from the photos table (already validated). Add a fallback placeholder image.
**Warning signs:** Blank image in recipe card.

### Pitfall 4: Gemini Nano Prompt Token Limit
**What goes wrong:** Adding recipe_name to prompt causes truncation.
**Why it happens:** Gemini Nano has a 256-token output limit (from existing comments in geminiNanoService.ts).
**How to avoid:** recipe_name is a short string (3-5 words). Fits easily. But test with complex multi-dish photos.
**Warning signs:** JSON parse failure after prompt modification.

### Pitfall 5: Update All Rewriting History
**What goes wrong:** User accidentally overwrites weeks of diary entries.
**Why it happens:** "Update all" is destructive and irreversible.
**How to avoid:** Show a clear warning with entry count ("This will update 14 diary entries"). Consider storing the old ingredient snapshot in modification_history.
**Warning signs:** User complaints about changed historical totals.

## Open Questions

1. **Should favourites and recipes coexist or merge?**
   - What we know: Favourites store only macro totals. Recipes store ingredients. Both appear on EntryDetailScreen.
   - What's unclear: Whether users need both concepts.
   - Recommendation: Keep both for now. Favourites are quick (no ingredients), recipes are detailed. They serve different use cases.

2. **How to handle "Update All" for entries with manual edits?**
   - What we know: Some diary entries may have been manually edited after logging from a recipe.
   - What's unclear: Should "Update All" overwrite manual edits?
   - Recommendation: Only update entries where user_modified = false on all ingredients. Warn about entries with manual edits.

3. **Android Alert.prompt unavailability**
   - What we know: Alert.prompt is iOS-only. Android needs a custom modal for text input.
   - What's unclear: N/A -- this is a known platform limitation.
   - Recommendation: Use a cross-platform TextInput modal (same pattern as import URL modal in RecipeScreen).
