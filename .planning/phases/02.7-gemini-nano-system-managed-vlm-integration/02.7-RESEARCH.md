## Summary

Phase 2.7 adds Gemini Nano as Tier 0 in the food identification pipeline via the ML Kit GenAI Prompt API (`com.google.mlkit:genai-prompt:1.0.0-beta1`). The API graduated from alpha to beta on January 28, 2026, with a stable Kotlin interface. Device support is runtime-checked via `checkStatus()` returning `FeatureStatus.AVAILABLE/DOWNLOADABLE/DOWNLOADING/UNAVAILABLE` — no hardcoded model checks needed.

The implementation requires a new Expo native module (`GeminiNanoModule.kt`) living in `apps/mobile/modules/gemini-nano/` using the standard Expo Module API DSL. The module receives a `file://` or `content://` URI from JS, decodes it to a `Bitmap` in Kotlin, and passes it to `GenerateContentRequest.builder(ImagePart(bitmap), TextPart(prompt))`. Response is the raw text string returned to JS for JSON parsing. This mirrors the existing vlmService pattern.

Wave 1 is a quality spike: `GeminiNanoTestScreen` navigable from `ProfileScreen`'s "AI Models" section, showing raw Gemini Nano JSON output for evaluation. Wave 2 wires `geminiNanoService.ts` into `runVlmIdentification()` before the `vlmService.isReady` check.

**Primary recommendation:** Use `com.google.mlkit:genai-prompt:1.0.0-beta1` with `GenerativeModel.generateContent()` (synchronous, not streaming) for Wave 1 — simpler Kotlin/Coroutine integration, JSON response fits well within the 256-token output limit.

### Pattern 2: ML Kit GenAI Availability Check

**What:** Check `FeatureStatus` before every inference call.
**When to use:** Always — AICore state can change between app sessions.

```kotlin
// Source: https://developers.google.com/android/reference/kotlin/com/google/mlkit/genai/prompt/GenerativeModel
import com.google.mlkit.genai.prompt.Generation
import com.google.mlkit.genai.prompt.FeatureStatus

val model = Generation.getClient()
val status = model.checkStatus()
return when (status) {
    FeatureStatus.AVAILABLE -> "available"
    FeatureStatus.DOWNLOADING -> "downloading"
    FeatureStatus.DOWNLOADABLE -> "not_supported"  // system hasn't downloaded yet — treat as unavailable for now
    FeatureStatus.UNAVAILABLE -> "not_supported"
    else -> "not_supported"
}
```

Note on `DOWNLOADABLE`: AICore manages model downloads automatically on supported devices. If status is `DOWNLOADABLE`, Gemini Nano is supported but not yet downloaded by the OS. The app should NOT trigger a manual download — it is system-managed. Treat as temporarily unavailable and fall through to SmolVLM.

### Pattern 3: Multimodal Inference with ImagePart

**What:** Load bitmap from URI, pass to GenerateContentRequest with TextPart.
**When to use:** `identifyFood(imageUri, prompt)` in GeminiNanoModule.

```kotlin
// Source: https://developers.google.com/android/reference/kotlin/com/google/mlkit/genai/prompt/GenerateContentRequest
// Source: https://android-developers.googleblog.com/2025/10/ml-kit-genai-prompt-api-alpha-release.html
import com.google.mlkit.genai.prompt.GenerateContentRequest
import com.google.mlkit.genai.prompt.ImagePart
import com.google.mlkit.genai.prompt.TextPart
import android.graphics.BitmapFactory
import android.net.Uri
import java.io.InputStream

// Load bitmap from URI (handles both file:// and content://)
fun loadBitmapFromUri(uri: String): android.graphics.Bitmap {
    val androidUri = Uri.parse(uri)
    val inputStream: InputStream = if (androidUri.scheme == "content") {
        appContext.reactContext!!.contentResolver.openInputStream(androidUri)!!
    } else {
        java.io.FileInputStream(androidUri.path!!)
    }
    return BitmapFactory.decodeStream(inputStream)
}

// Build and execute request
val bitmap = loadBitmapFromUri(imageUri)
val request = GenerateContentRequest.builder(
    ImagePart(bitmap),
    TextPart(prompt)
).setTemperature(0.2f)
 .setMaxOutputTokens(256)
 .setTopK(10)
 .build()

val response = model.generateContent(request)
val text = response.candidates.firstOrNull()?.text ?: ""
```

### Anti-Patterns to Avoid

- **Calling `model.download()` from the app:** AICore manages model downloads; calling `download()` manually on a `DOWNLOADABLE` model is not recommended in the app flow. Let the OS handle it.
- **New `Generation.getClient()` per inference call:** `GenerativeModel` holds a binding to AICore. Reuse the instance across calls within a session. Releasing and recreating per-call adds latency.
- **Passing base64 image strings to Kotlin:** The existing VLM pipeline passes `file://` URIs to `vlmService.identify()`. Keep this pattern — decode the bitmap in Kotlin from the URI, not from base64.
- **Running inference in background:** AICore blocks inference when the app is not the top foreground application. Do not call `identifyFood` from background tasks or foreground services.
- **Ignoring `ErrorCode.BUSY`:** AICore enforces per-app quotas. Wrap inference in try/catch and treat `BUSY` as a transient failure — fall through to SmolVLM.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| AICore binding/session management | Custom AIDL binding | `Generation.getClient()` | Google manages the IPC, reconnection, and session lifecycle |
| Bitmap loading from URI | Manual URI scheme detection | `ContentResolver.openInputStream()` + `BitmapFactory.decodeStream()` | Handles `content://`, `file://`, media store URIs transparently |
| JSON schema enforcement | Custom regex/text parser in Kotlin | Prompt engineering + JSON.parse() in TypeScript (same as vlmService) | ML Kit has no grammar-constrained output; TypeScript parse is already proven |
| Device capability detection | Hardcoded Pixel model strings | `GenerativeModel.checkStatus()` → `FeatureStatus` | Official API; works across all AICore-enabled devices without maintenance |

**Key insight:** The entire complexity of AICore device compatibility, model versioning, and inference scheduling is hidden behind `Generation.getClient()`. The app should never reach into AICore internals.

## Common Pitfalls

### Pitfall 1: Unlocked Bootloader Blocks Inference
**What goes wrong:** `checkStatus()` returns `UNAVAILABLE` even on a supported Pixel device. Inference calls throw an error.
**Why it happens:** AICore enforces device integrity — unlocked bootloaders are blocked from Gemini Nano access.
**How to avoid:** Test only on stock/locked devices. Emulator is also blocked — emulator testing for this module is limited to module loading and UI rendering only (not actual inference).
**Warning signs:** `UNAVAILABLE` status on a Pixel 9 Pro with a developer-unlocked bootloader.

### Pitfall 2: AICore Not Initialized After Fresh Device Setup
**What goes wrong:** `checkStatus()` returns `UNAVAILABLE` or API calls fail with binding errors immediately after device reset or factory restore.
**Why it happens:** AICore needs time after first boot to download configuration from Google servers.
**How to avoid:** In `checkAvailability()`, catch binding/initialization exceptions and return `'not_supported'` rather than crashing. Fallthrough to SmolVLM.
**Warning signs:** Consistent `UNAVAILABLE` status on a known-good device that works after a restart or waiting period.

### Pitfall 3: `ErrorCode.BUSY` from Inference Quota
**What goes wrong:** `generateContent()` throws an exception with `ErrorCode.BUSY` during repeated rapid calls.
**Why it happens:** AICore enforces per-app inference quotas. Rapid re-identification (e.g., user types in MealTextInput triggering multiple VLM calls in 500ms) can exceed quota.
**How to avoid:** The 500ms debounce in `handleUserTextChange` already exists. For Gemini Nano, add a catch for `BUSY` error and fall through to SmolVLM for that call.
**Warning signs:** Errors increase during rapid text-input re-identification.

### Pitfall 4: `DOWNLOADABLE` Status Misinterpreted as Permanent Failure
**What goes wrong:** App treats `DOWNLOADABLE` as "not supported" permanently and always uses SmolVLM even though Gemini Nano would become available after AICore downloads.
**Why it happens:** `DOWNLOADABLE` means the device supports Gemini Nano but AICore hasn't downloaded it yet (e.g., new SIM, roaming, battery saver prevented download).
**How to avoid:** Cache the availability result but re-check at next app launch (session-scoped cache, not persistent). If `DOWNLOADABLE`, return `'not_supported'` for the current session but do NOT write a permanent "not supported" flag.
**Warning signs:** Pixel 9 Pro always falls back to SmolVLM.

### Pitfall 5: Content URI from Gallery Picker Fails in Kotlin
**What goes wrong:** `FileInputStream(uri.path)` throws `FileNotFoundException` for `content://` URIs from the gallery.
**Why it happens:** `content://` URIs are MediaStore handles, not filesystem paths. `uri.path` is not a valid file path for content URIs.
**How to avoid:** Check URI scheme before opening. Use `ContentResolver.openInputStream()` for `content://`, `FileInputStream` for `file://`. The existing VLM pipeline uses `expo-image-picker` which returns `file://` URIs — but be defensive.
**Warning signs:** Crash on images from the gallery picker in GeminiNanoTestScreen.

### Pitfall 6: `maxOutputTokens` Default (256) May Truncate JSON
**What goes wrong:** JSON response is cut off mid-object, causing parse failure in the TypeScript layer.
**Why it happens:** The API hard-caps at 256 tokens. A `VlmFoodResult` with 3-4 dishes including ingredients can approach this limit.
**How to avoid:** Use concise prompts. In the spike, ask for minimal fields: name, cuisine only. Do not ask for full ingredients array in Wave 1. If parse fails, return `{ dishes: [] }` (same fallback as vlmService).
**Warning signs:** JSON.parse() throws `SyntaxError: Unexpected end of JSON input`.

### Full GeminiNanoModule.kt Skeleton
```kotlin
// Source: https://docs.expo.dev/modules/module-api/ + https://developers.google.com/android/reference/kotlin/com/google/mlkit/genai/prompt/GenerativeModel
package expo.modules.geminanano

import android.graphics.BitmapFactory
import android.net.Uri
import com.google.mlkit.genai.prompt.FeatureStatus
import com.google.mlkit.genai.prompt.GenerateContentRequest
import com.google.mlkit.genai.prompt.Generation
import com.google.mlkit.genai.prompt.ImagePart
import com.google.mlkit.genai.prompt.TextPart
import expo.modules.kotlin.Promise
import expo.modules.kotlin.modules.Module
import expo.modules.kotlin.modules.ModuleDefinition

class GeminiNanoModule : Module() {

    // Reuse across calls in the same app session
    private val model by lazy { Generation.getClient() }

    override fun definition() = ModuleDefinition {
        Name("GeminiNano")

        AsyncFunction("checkAvailability") Coroutine { ->
            try {
                when (model.checkStatus()) {
                    FeatureStatus.AVAILABLE -> "available"
                    FeatureStatus.DOWNLOADING -> "downloading"
                    else -> "not_supported"
                }
            } catch (e: Exception) {
                "not_supported"
            }
        }

        AsyncFunction("identifyFood") Coroutine { imageUri: String, prompt: String ->
            val androidUri = Uri.parse(imageUri)
            val stream = if (androidUri.scheme == "content") {
                appContext.reactContext!!.contentResolver.openInputStream(androidUri)!!
            } else {
                java.io.FileInputStream(androidUri.path!!)
            }
            val bitmap = BitmapFactory.decodeStream(stream)

            val request = GenerateContentRequest
                .builder(ImagePart(bitmap), TextPart(prompt))
                .setTemperature(0.2f)
                .setMaxOutputTokens(256)
                .setTopK(10)
                .build()

            val response = model.generateContent(request)
            response.candidates.firstOrNull()?.text ?: ""
        }
    }
}
```

### Availability Check in geminiNanoService.ts (Wave 2)
```typescript
// Source: pattern mirrors ramDetector.ts singleton pattern in this project
let _cachedAvailability: boolean | null = null;

export const geminiNanoService = {
  async isAvailable(): Promise<boolean> {
    if (_cachedAvailability !== null) return _cachedAvailability;
    try {
      const status = await geminiNanoModule.checkAvailability();
      _cachedAvailability = status === 'available';
    } catch {
      _cachedAvailability = false;
    }
    if (__DEV__) {
      console.log('[GeminiNano] Availability:', _cachedAvailability);
    }
    return _cachedAvailability;
  },

  async identify(photoUri: string, userText?: string): Promise<VlmFoodResult> {
    const raw = await geminiNanoModule.identifyFood(photoUri, FOOD_PROMPT);
    try {
      const parsed = JSON.parse(raw) as VlmFoodResult;
      if (parsed.dishes?.length > 0) return parsed;
    } catch { /* fall through */ }
    return { dishes: [] };
  },
};
```

## Existing VLM Architecture (Integration Seam)

### vlmService.ts Interface

The `vlmService` singleton exposes:
- `init(modelPath, mmprojPath): Promise<void>` — loads GGUF model
- `identify(imageUri, userText?): Promise<VlmFoodResult>` — runs inference
- `release(): Promise<void>` — frees RAM
- `isReady: boolean` — getter, true when context is loaded

**GeminiNanoService must expose:**
- `isAvailable(): Promise<boolean>` — checks AICore readiness (replaces `isReady` which is synchronous)
- `identify(imageUri, userText?): Promise<VlmFoodResult>` — same signature
- No `init()` or `release()` needed — AICore is system-managed

### vlmPipeline.ts Integration Point

`runVlmIdentification()` at line 88-91:
```typescript
// Current guard (line 89):
if (!vlmService.isReady) {
  throw new Error('VLM model is not loaded. Download the VLM pack first.');
}
```

Wave 2 inserts Tier 0 check BEFORE this guard. The rest of `runVlmIdentification()` (positional matching, KG lookup, item enrichment) is reusable — both Gemini Nano and SmolVLM return `VlmFoodResult`, so the downstream code is identical.

### VlmFoodResult Shape
```typescript
// vlmTypes.ts (exact, verified)
interface VlmDish {
  name: string;
  cuisine: string;         // required
  ingredients: string[];   // required
  portion_hint?: string;   // optional
}
interface VlmFoodResult {
  dishes: VlmDish[];
}
```

The Wave 1 spike prompt should ask for `name`, `cuisine`, `ingredients` (matching `required` in `FOOD_IDENTIFICATION_SCHEMA`). `portion_hint` is optional and can be omitted from the spike prompt.

### Image URI Format

From `DetectionScreen.tsx` lines 422-431 and 449-458:
- Camera: `expo-image-picker launchCameraAsync` → returns `asset.uri` which is a `file://` URI
- Gallery: `expo-image-picker launchImageLibraryAsync` → returns `asset.uri` which may be `content://` on Android

Both paths call `setPhoto(asset.uri, ...)` which is then passed to `vlmService.identify(photoUri!, ...)`.

**Conclusion:** The `imageUri` parameter in `GeminiNanoModule.identifyFood` will be `file://...` from camera and `content://...` from gallery. Both cases must be handled in Kotlin (see Pattern 3 above).

### Navigation Structure

`RootNavigator.tsx` uses `createNativeStackNavigator` with routes: `Main`, `Detection`, `VlmDownload`. `GeminiNanoTest` should be added as a 4th stack screen with `headerShown: true`, `headerTitle: 'Gemini Nano Test'`.

The **natural entry point** is `ProfileScreen.tsx` lines 52-61, which already has an "AI Models" section with a "VLM Model → Manage" row. A second row "Gemini Nano Test → Debug" follows the same `rootNavigation.navigate(...)` pattern already used there.

## Open Questions

1. **Session reuse vs. per-call `Generation.getClient()`**
   - What we know: `GenerativeModel` holds an AICore binding. The reference docs show `close()` for cleanup.
   - What's unclear: Whether repeatedly calling `Generation.getClient()` creates multiple bindings or returns a shared instance.
   - Recommendation: Use `private val model by lazy { Generation.getClient() }` in the module class (module-scoped singleton, created once per module lifetime). Call `model.close()` in the module's `onDestroy` if the Expo Module API exposes a lifecycle hook.

2. **`DOWNLOADABLE` state behavior in practice on Pixel 9 Pro**
   - What we know: Pixel 9 Pro should ship with Gemini Nano pre-downloaded by AICore. `DOWNLOADABLE` should not appear on a fresh Pixel 9 Pro.
   - What's unclear: Whether a recently factory-reset Pixel 9 Pro shows `DOWNLOADABLE` before AICore re-downloads.
   - Recommendation: In the spike, log the raw `FeatureStatus` value to console so the user can report back what they see on their device.

3. **Bitmap scale/size requirements**
   - What we know: The ML Kit docs mention "reduced latency of processing large images" in beta. No explicit max resolution stated.
   - What's unclear: Whether passing a full 12MP camera photo (4032x3024) causes excessive latency or errors.
   - Recommendation: Scale the bitmap down to 1024px on the longest edge before passing to `ImagePart`. This is safe and matches what the Image Description API does internally.
