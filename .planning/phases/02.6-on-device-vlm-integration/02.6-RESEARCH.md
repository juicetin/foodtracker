# Phase 2.6: On-Device VLM Integration - Research

**Researched:** 2026-03-14
**Domain:** On-device vision-language model inference (llama.rn + SmolVLM), PackManager streaming downloads, progressive detection refinement UI
**Confidence:** HIGH

## Summary

This phase integrates a SmolVLM vision-language model (VLM) into the existing YOLO detection pipeline using llama.rn as the inference runtime. The VLM acts as an asynchronous refinement layer: YOLO provides instant bounding boxes (50-80ms), then the VLM processes the full image plus optional user text to produce richer food identifications (1-3s) that are fed into the Knowledge Graph for nutrition lookup.

The core technical challenge has three pillars: (1) llama.rn integration for multimodal GGUF inference with grammar-constrained JSON output, (2) PackManager overhaul to stream 300MB+ VLM downloads without OOM crashes, and (3) a progressive UI that shows detection results immediately and upgrades labels in-place as VLM refinement completes. Device RAM detection via expo-device gates which SmolVLM tier is downloaded and loaded.

**Primary recommendation:** Build a VlmService abstraction that manages llama.rn context lifecycle (init, infer, release), keeping VLM completely decoupled from the TFLite YOLO pipeline. Use the legacy expo-file-system `createDownloadResumable` for large file downloads (streams to disk, supports progress and pause/resume). Add `isRefining` and `vlmLabel` fields to DetectedItem for the progressive label transition.

### Pattern 1: VlmService Singleton with Lazy Loading
**What:** A singleton service that manages the llama.rn context lifecycle. Loads VLM model lazily on first detection, keeps it warm during session, releases on inactivity timeout.
**When to use:** Always -- VLM context is expensive to create (~1-3s) and should be reused.
**Example:**
```typescript
// Source: llama.rn README + project patterns
import { initLlama, type LlamaContext } from 'llama.rn';

class VlmService {
  private context: LlamaContext | null = null;
  private releaseTimer: NodeJS.Timeout | null = null;

  async init(modelPath: string, mmprojPath: string): Promise<void> {
    if (this.context) return; // already initialized

    this.context = await initLlama({
      model: modelPath,
      n_ctx: 2048,
      n_gpu_layers: 99,  // offload to GPU when available
      use_mlock: true,
      ctx_shift: false,   // REQUIRED for multimodal
    });

    await this.context.initMultimodal({
      path: mmprojPath,
      use_gpu: true,
    });
  }

  async identify(imageUri: string, userText?: string): Promise<VlmFoodResult> {
    if (!this.context) throw new Error('VLM not initialized');
    this.resetReleaseTimer();

    const result = await this.context.completion({
      messages: [{
        role: 'user',
        content: [
          { type: 'image_url', image_url: { url: imageUri } },
          { type: 'text', text: buildFoodPrompt(userText) },
        ],
      }],
      response_format: {
        type: 'json_schema',
        json_schema: { /* food identification schema */ }
      },
      n_predict: 256,
      temperature: 0.1,  // low temp for structured output
    });

    return JSON.parse(result.text);
  }

  async release(): Promise<void> {
    if (this.context) {
      await this.context.release();
      this.context = null;
    }
  }
}
```

### Pattern 2: Progressive Refinement Pipeline
**What:** YOLO results display instantly, then VLM refines asynchronously. Labels update in-place with animation.
**When to use:** Every detection flow when VLM is available.
**Example:**
```typescript

  setIsRefining(true);
```

### Pattern 3: Streaming Download with Progress
**What:** Use legacy createDownloadResumable for VLM model downloads (300MB+). Writes directly to disk, provides progress callbacks.
**When to use:** All VLM pack downloads. Never use `fetch().arrayBuffer()` for files >50MB.
**Example:**
```typescript
// Source: expo-file-system legacy API
import * as FileSystemLegacy from 'expo-file-system/legacy';

const downloadResumable = FileSystemLegacy.createDownloadResumable(
  packUrl,
  localFilePath,
  { headers: { 'X-API-Key': apiKey } },
  (progress) => {
    onProgress({
      totalBytesWritten: progress.totalBytesWritten,
      totalBytesExpected: progress.totalBytesExpectedToWrite,
      fraction: progress.totalBytesWritten / progress.totalBytesExpectedToWrite,
    });
  }
);
const result = await downloadResumable.downloadAsync();
```

### Anti-Patterns to Avoid
- **Loading VLM at app boot:** VLM context takes 1-3s and ~300-500MB RAM. Load lazily on first detection, not at startup.
- **Running VLM on crops:** Send full image, not individual YOLO crops. SmolVLM reasons better about whole-plate context.
- **Blocking UI on VLM:** VLM inference takes 1-3s. Always show YOLO results first, refine asynchronously.
- **Keeping VLM warm indefinitely:** Release context after 60s inactivity. Mobile apps get killed for holding RAM.
- **Using fetch().arrayBuffer() for VLM downloads:** Will OOM on 300MB+ files. Must use streaming download.
- **Enabling ctx_shift for multimodal:** llama.rn requires `ctx_shift: false` for multimodal models. Enabling it causes crashes.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| JSON schema to GBNF grammar | Custom grammar parser | llama.rn built-in `response_format: { type: 'json_schema' }` | llama.rn converts json_schema to GBNF internally; always valid JSON output |
| Large file streaming download | Custom fetch+write chunking | `createDownloadResumable` from expo-file-system/legacy | Native-level streaming, progress callbacks, pause/resume, direct-to-disk writes |
| Model quantization/conversion | Custom GGUF conversion | Pre-converted ggml-org models from HuggingFace | Official conversions tested against llama.cpp; multiple quant levels available |
| Device RAM detection | Platform-specific native modules | expo-device `totalMemory` | Works on iOS + Android, returns bytes, null-safe for web |
| VLM text template formatting | String concatenation prompts | Structured prompt builder with chat template | llama.rn applies the model's chat template automatically via messages API |

**Key insight:** llama.rn handles the hard parts (GGUF loading, GPU offloading, grammar constraints, chat templates, multimodal token placement). The app's job is lifecycle management and UI orchestration.

## Common Pitfalls

### Pitfall 1: OOM During VLM Download
**What goes wrong:** Current PackManager uses `fetch().arrayBuffer()` which loads the entire response into RAM before writing to disk. A 300MB SmolVLM download will crash on 4GB devices.
**Why it happens:** The v19 expo-file-system `File.downloadFileAsync()` also appears to buffer in memory. The legacy `createDownloadResumable` is the only Expo-native API that streams to disk.
**How to avoid:** Use `createDownloadResumable` from `expo-file-system/legacy` for all VLM downloads. Import from `'expo-file-system/legacy'` specifically.
**Warning signs:** App crashes with no error during download; Android low-memory killer terminates app.

### Pitfall 2: ctx_shift Must Be Disabled for Multimodal
**What goes wrong:** Enabling `ctx_shift: true` (the default) with multimodal models causes crashes or garbled output.
**Why it happens:** Context shifting relocates tokens in the KV cache, which invalidates the positional mapping of image embeddings.
**How to avoid:** Always pass `ctx_shift: false` in `initLlama()` options for multimodal models.
**Warning signs:** Crash during `context.completion()` with image input; nonsensical text output.

### Pitfall 3: Memory Pressure with Two Inference Engines
**What goes wrong:** YOLO models (~20MB) + VLM context (~300-500MB) + app overhead can exceed available RAM on 4GB devices.
**Why it happens:** Both react-native-fast-tflite and llama.rn hold model weights in memory simultaneously.
**How to avoid:** Load VLM after YOLO inference completes (YOLO models stay loaded, they're tiny). Monitor device memory. On 4GB devices, use SmolVLM-256M Q8_0 (175MB model + 190MB mmproj = 365MB total download, ~500MB runtime).
**Warning signs:** App termination by OS low-memory killer; thermal throttling during concurrent inference.

### Pitfall 4: VLM Hallucination on Food Items
**What goes wrong:** SmolVLM confidently identifies food incorrectly (e.g., "beef stew" when it's actually "massaman curry"). Grammar constraints prevent structural errors but not semantic errors.
**Why it happens:** SmolVLM is trained on general data, not food-specific data. It may struggle with unfamiliar cuisines or similar-looking dishes.
**How to avoid:** Use VLM output as a refinement signal, not replacement. Keep YOLO label as fallback. Set VLM confidence thresholds. When VLM and YOLO disagree significantly, prefer YOLO. Allow user correction.
**Warning signs:** VLM labels consistently worse than YOLO labels for certain food categories.

### Pitfall 5: Paired File Download Atomicity
**What goes wrong:** Model GGUF downloads successfully but mmproj download fails. Pack is recorded as "installed" but unusable.
**Why it happens:** Current PackManager records install after single file download. VLM packs need both files.
**How to avoid:** Download both files before recording the pack as installed. If either fails, clean up both files. Make the install recording atomic (insert only after both files verified).
**Warning signs:** VLM init fails with "mmproj not found" despite pack showing as installed.

### Pitfall 6: New Architecture Requirement
**What goes wrong:** llama.rn v0.10+ fails to initialize or crashes at runtime.
**Why it happens:** llama.rn v0.10+ requires React Native New Architecture (Fabric/TurboModules). Old Architecture not supported.
**How to avoid:** Already enabled in this project (`newArchEnabled: true` in app.json). No action needed, but verify during testing.
**Warning signs:** Native module not found errors; linker errors during build.

```typescript
// Prompt designed for grammar-constrained JSON output
function buildFoodPrompt(userText?: string): string {
  const base = `Identify all food items visible in this image. For each food item, provide:
- name: the specific dish or food name (e.g., "massaman curry" not just "curry")
- cuisine: the cuisine type (e.g., "Thai", "Italian", "Japanese")
- ingredients: list of likely main ingredients
- portion_hint: estimated portion description (e.g., "large bowl", "single serving")`;

  if (userText) {
    return `${base}\n\nThe user describes this meal as: "${userText}". Use this context to improve identification accuracy.`;
  }
  return base;
```

### RAM-Based Tier Selection
```typescript
// Source: expo-device docs
import * as Device from 'expo-device';

export type VlmTier = 'budget' | 'mid' | 'high' | 'none';

export function detectVlmTier(): VlmTier {
  const totalBytes = Device.totalMemory;
  if (totalBytes == null) return 'none'; // web or unsupported

  const totalGB = totalBytes / (1024 ** 3);

  if (totalGB >= 8) return 'high';    // SmolVLM2-2.2B Q4
  if (totalGB >= 6) return 'mid';     // SmolVLM-500M Q8
  if (totalGB >= 4) return 'budget';  // SmolVLM-256M Q8
  return 'none'; // <4GB -- VLM not recommended
}

export const VLM_TIER_CONFIG = {
  budget: {
    modelId: 'smolvlm-256m-q8',
    modelFile: 'SmolVLM-256M-Instruct-Q8_0.gguf',
```

### Streaming Download for PackManager
```typescript
// Import legacy API for streaming downloads
import * as FileSystemLegacy from 'expo-file-system/legacy';

async function downloadLargeFile(
  url: string,
  destPath: string,
  headers: Record<string, string>,
  onProgress: (progress: DownloadProgress) => void,
): Promise<void> {
  const downloadResumable = FileSystemLegacy.createDownloadResumable(
    url,
    destPath,
    { headers },
    ({ totalBytesWritten, totalBytesExpectedToWrite }) => {
      onProgress({
        totalBytesWritten,
        totalBytesExpected: totalBytesExpectedToWrite,
        fraction: totalBytesExpectedToWrite > 0
          ? totalBytesWritten / totalBytesExpectedToWrite
          : 0,
      });
    }
  );

  const result = await downloadResumable.downloadAsync();
  if (!result) {
    throw new Error('Download failed: no result returned');
  }
}
```

## Open Questions

1. **SmolVLM2-2.2B mmproj exact file size**
   - What we know: Q4_K_M model is 1.11 GB; mmproj should be similar to 256M/500M mmproj (~109-199 MB)
   - What's unclear: Exact mmproj size for SmolVLM2-2.2B from ggml-org repo
   - Recommendation: Download and verify during implementation; use 190 MB estimate for planning

2. **VLM inference latency on budget devices**
   - What we know: SmolVLM-256M is the smallest VLM; general benchmarks suggest 500ms-1s for short responses
   - What's unclear: No published mobile-specific benchmarks for SmolVLM-256M food identification latency
   - Recommendation: Benchmark during implementation; set 5s timeout with graceful fallback to YOLO-only

3. **VLM-to-YOLO bounding box matching**
   - What we know: VLM processes full image and outputs dish names; YOLO provides spatial bounding boxes
   - What's unclear: Best strategy to match VLM dish names to specific YOLO bounding boxes (string similarity? spatial reasoning? order-based?)
   - Recommendation: Use fuzzy string matching (VLM dish name vs YOLO class name) as primary matching. If VLM identifies more/fewer items than YOLO boxes, fall back to order-based or leave unmatched items unchanged.

4. **expo-file-system/legacy import availability in v19**
   - What we know: Expo docs list legacy API as importable from `expo-file-system/legacy`
   - What's unclear: Whether this import path works cleanly in the project's current Expo SDK 54 setup
   - Recommendation: Test import early; if broken, fall back to react-native-blob-util as streaming download alternative
