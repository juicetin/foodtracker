# Phase 3.5: OFF Cache + Attribution - Context

**Gathered:** 2026-03-19
**Status:** Ready for planning

<domain>
## Phase Boundary

SQLite cache layer for Open Food Facts API responses enabling offline food lookups, with adaptive rate limiting respecting OFF's per-IP limits (100 product/min, 10 search/min), and ODbL attribution in the app UI. Cache is included in all data exports and backups.

</domain>

<decisions>
## Implementation Decisions

### Cache storage
- SQLite table in the main user DB (opsqlite) — not a separate database
- Two tables: `off_product_cache` (keyed by barcode) and `off_search_cache` (keyed by normalized query)
- Store full JSON response blob + parsed key fields (name, brand, nutrition per 100g)
- Include `cached_at` timestamp for staleness checks

### Cache strategy
- Stale-while-revalidate: serve cached result immediately, refresh from network in background
- Barcode products: stale after 7 days (products rarely change)
- Search results: stale after 24 hours (search ranking may shift)
- No cache eviction — data grows organically with user's food choices, stays small
- When rate limited or offline, serve cached results silently

### Rate limiting
- Adaptive rate limiter already built (rateLimiter.ts) — tracks rolling 60s window per request type
- Delay ramps from 0 to 6s between 60-100% of limit
- At limit: serve cached results if available, show user-facing message if not
- Message mentions VPN/shared IP as possible cause (OFF limits are per-IP, shared networks share quota)

### Attribution
- ODbL attribution link in Profile screen's About section
- Text: "Food product data provided by Open Food Facts" with link to openfoodfacts.org
- No splash screen or prominent placement needed — About section is legally sufficient

### Export integration
- OFF cache included in CSV and JSON exports (separate section)
- OFF cache included in incremental backup system (Phase 3.6)
- Cache data travels with user to new device via backup restore

### Claude's Discretion
- Exact SQLite schema for cache tables
- Background refresh implementation (setTimeout vs event-driven)
- Whether to show a subtle "cached" indicator on results served from cache

</decisions>
