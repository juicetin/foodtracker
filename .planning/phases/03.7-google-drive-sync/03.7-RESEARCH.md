# Phase 3.7: Google Drive Sync - Research

**Researched:** 2026-03-21
**Domain:** Google Drive API integration, OAuth, background sync
**Confidence:** MEDIUM-HIGH

## Summary

This phase adds a Google Drive cloud transport layer on top of the existing Phase 3.6 incremental backup system. The core challenge is OAuth token management, binary file upload/download to Drive's appdata folder, WiFi-only gating, and a conflict resolution UI for the rare multi-device case.

Two library approaches exist: (1) `react-native-cloud-storage` v3.0.0 which provides a high-level fs-like API wrapping Drive REST, paired with `@react-native-google-signin/google-signin` for auth tokens; or (2) direct Google Drive REST API v3 calls using `fetch()` with tokens from google-signin. The recommended approach is `react-native-cloud-storage` for file operations (it has `uploadFile`/`downloadFile` that handle binary .db files via local paths) with `@react-native-google-signin/google-signin` v16 for OAuth -- this minimizes hand-rolled Drive API code while keeping full control over auth scopes.

The appdata folder (`drive.appdata` scope) is hidden from the user's Drive UI, requires no Google security audit, and counts against the user's 15GB quota. For the optional custom folder feature, `drive.file` scope is needed -- this is a "sensitive" (not restricted) scope that requires a consent screen but no audit.

**Primary recommendation:** Use `@react-native-google-signin/google-signin` v16 for OAuth + `react-native-cloud-storage` v3 for Drive file operations. Direct REST API calls only as fallback for edge cases not covered by the library.

### Pattern 1: Token-First Auth Flow
**What:** Sign in with google-signin, extract access token, pass to react-native-cloud-storage
**When to use:** Every sync operation
**Example:**
```typescript
// Source: react-native-google-signin docs + react-native-cloud-storage docs
import { GoogleSignin } from '@react-native-google-signin/google-signin';
import { CloudStorage, CloudStorageScope } from 'react-native-cloud-storage';

async function ensureDriveAccess(): Promise<void> {
  const tokens = await GoogleSignin.getTokens();
  CloudStorage.setProviderOptions({ accessToken: tokens.accessToken });
}
```

### Pattern 2: Multipart Upload for Binary Files
**What:** Use `CloudStorage.uploadFile()` for .db files, `CloudStorage.writeFile()` for JSON incrementals
**When to use:** Full backup = uploadFile (binary), incremental = writeFile (JSON string)
**Example:**
```typescript
// Full backup upload (binary .db file)
await CloudStorage.uploadFile(
  '/backups/tastimate-backup-full-2026-03-21.db',
  localDbPath,
  { mimeType: 'application/x-sqlite3' },
  CloudStorageScope.AppData
);

// Incremental upload (JSON string)
const json = await file.text();
await CloudStorage.writeFile(
  '/backups/tastimate-backup-incremental-2026-03-21.json',
  json,
  CloudStorageScope.AppData
);
```

### Pattern 3: Scope Escalation for Custom Folder
**What:** Start with `drive.appdata`, upgrade to `drive.file` only if user picks custom folder
**When to use:** When user enables "Save to visible Drive folder" in settings
**Example:**
```typescript
// Initial config with appdata only
GoogleSignin.configure({
  scopes: ['https://www.googleapis.com/auth/drive.appdata'],
  webClientId: 'YOUR_WEB_CLIENT_ID',
});

// Escalate when user wants custom folder
await GoogleSignin.addScopes({
  scopes: ['https://www.googleapis.com/auth/drive.file'],
});
```

### Pattern 4: WiFi-Gated Sync
**What:** Check NetInfo before sync; skip if not WiFi and user has WiFi-only enabled
**When to use:** Every auto-sync trigger
**Example:**
```typescript
import NetInfo from '@react-native-community/netinfo';

async function shouldSync(wifiOnly: boolean): Promise<boolean> {
  if (!wifiOnly) return true;
  const state = await NetInfo.fetch();
  return state.type === 'wifi' && state.isConnected === true;
}
```

### Anti-Patterns to Avoid
- **Storing access tokens in AsyncStorage:** google-signin manages tokens natively; calling `getTokens()` always returns current valid tokens (iOS refreshes automatically, Android requires clearCachedAccessToken on 401)
- **Uploading full backup every sync:** Use the existing incremental system; only upload changed incrementals + periodic full compaction
- **Blocking UI on sync:** All sync operations must be async with progress/status UI, never blocking navigation
- **Using drive scope instead of drive.appdata:** The full `drive` scope is restricted and requires Google security audit. `drive.appdata` and `drive.file` are sufficient and only require consent screen.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Google OAuth flow | Custom WebView OAuth | @react-native-google-signin/google-signin | Native SDK handles token refresh, credential storage, consent screen |
| Drive file upload/download | Raw fetch() multipart | react-native-cloud-storage uploadFile/downloadFile | Handles multipart encoding, pagination, error responses |
| Network type detection | Navigator.connection or manual checks | @react-native-community/netinfo | Cross-platform, handles edge cases (VPN, metered WiFi) |
| Background scheduling | Custom AlarmManager/Timer | expo-background-task (already installed) | OS-managed scheduling, battery-optimized, already in project |
| Token refresh logic | Manual refresh token management | google-signin getTokens() | Native SDK handles refresh automatically per-platform |

**Key insight:** The Drive REST API multipart upload format is finicky (boundary strings, content-type headers, metadata+body parts). react-native-cloud-storage abstracts this completely.

## Common Pitfalls

### Pitfall 1: Access Token Expiry During Long Upload
**What goes wrong:** Token expires mid-upload of a large full backup .db file
**Why it happens:** Google access tokens expire after 1 hour; full backup could be 50-80MB on slow connection
**How to avoid:** Call `getTokens()` immediately before each upload operation (not once at sync start). For large files, consider chunked/resumable upload.
**Warning signs:** 401 errors mid-sync, partial uploads

### Pitfall 2: Android getTokens() Returns Stale Token
**What goes wrong:** On Android, `getTokens()` can return a cached expired token
**Why it happens:** Android native layer caches tokens; doesn't auto-refresh like iOS
**How to avoid:** On 401 response, call `GoogleSignin.clearCachedAccessToken(staleToken)` then retry `getTokens()`
**Warning signs:** Sync works on iOS but fails on Android after ~1 hour

### Pitfall 3: AppData Folder Not Discoverable on Fresh Install
**What goes wrong:** User installs on new device, expects to find their backups, but appdata is app-specific
**Why it happens:** AppData folder is tied to the OAuth client ID, not the user's Google account per se -- if client ID differs between builds, folder is invisible
**How to avoid:** Use the SAME OAuth client ID across all builds (dev, staging, prod). Document this clearly.
**Warning signs:** Restore shows "no backups found" on new device despite data existing

### Pitfall 4: Filename Conflicts in Google Drive
**What goes wrong:** Google Drive allows multiple files with the same name; listing returns duplicates
**Why it happens:** Drive is not a filesystem -- names are not unique identifiers
**How to avoid:** Always use file ID for operations after initial list. Include unique backup ID in filenames. react-native-cloud-storage defaults to first match.
**Warning signs:** Duplicate backup files accumulating, wrong file downloaded

### Pitfall 5: Background Task Limitations
**What goes wrong:** Background sync never runs or runs unreliably
**Why it happens:** Android WorkManager has minimum 15-minute interval; OS can defer tasks; Doze mode throttles
**How to avoid:** Don't rely solely on background sync. Provide manual "Sync Now" button. Show last sync time prominently. Accept that background sync is best-effort.
**Warning signs:** Users report "last synced 3 days ago" despite daily usage

### Pitfall 6: drive.file Scope Requires Google Verification
**What goes wrong:** Custom folder feature triggers OAuth consent warning screen
**Why it happens:** `drive.file` is a "sensitive" scope requiring Google Cloud Console verification
**How to avoid:** For development/testing, add test users in Google Cloud Console. For production, submit verification form (takes days, not weeks). Note: `drive.appdata` does NOT require verification.
**Warning signs:** "This app isn't verified" warning screen during sign-in

## Code Examples

### Google Sign-In Configuration
```typescript
// Source: react-native-google-signin docs
import { GoogleSignin, statusCodes } from '@react-native-google-signin/google-signin';

GoogleSignin.configure({
  scopes: ['https://www.googleapis.com/auth/drive.appdata'],
  webClientId: 'YOUR_WEB_CLIENT_ID.apps.googleusercontent.com',
  offlineAccess: false, // No server-side token exchange needed
});

export async function signInToGoogle() {
  try {
    await GoogleSignin.hasPlayServices();
    const userInfo = await GoogleSignin.signIn();
    return userInfo;
  } catch (error: any) {
    if (error.code === statusCodes.SIGN_IN_CANCELLED) {
      // User cancelled
    } else if (error.code === statusCodes.IN_PROGRESS) {
      // Already signing in
    } else if (error.code === statusCodes.PLAY_SERVICES_NOT_AVAILABLE) {
      // Play services not available
    }
    throw error;
  }
}
```

### Drive File Operations with react-native-cloud-storage
```typescript
// Source: react-native-cloud-storage docs
import { CloudStorage, CloudStorageScope } from 'react-native-cloud-storage';

// List all backups in appdata
async function listRemoteBackups(): Promise<string[]> {
  const exists = await CloudStorage.exists('/backups', CloudStorageScope.AppData);
  if (!exists) return [];
  // readdir-like listing not shown; use stat or exists per-file
  return []; // Implementation detail
}

// Upload incremental JSON backup
async function uploadIncremental(filename: string, jsonContent: string): Promise<void> {
  await CloudStorage.writeFile(
    `/backups/${filename}`,
    jsonContent,
    CloudStorageScope.AppData
  );
}

// Upload full .db backup from local path
async function uploadFullBackup(filename: string, localPath: string): Promise<void> {
  await CloudStorage.uploadFile(
    `/backups/${filename}`,
    localPath,
    { mimeType: 'application/x-sqlite3' },
    CloudStorageScope.AppData
  );
}

// Download full .db backup to local path
async function downloadFullBackup(remoteName: string, localPath: string): Promise<void> {
  await CloudStorage.downloadFile(
    `/backups/${remoteName}`,
    localPath,
    CloudStorageScope.AppData
  );
}
```

### Token Refresh with Retry Pattern
```typescript
// Robust token handling for Android
async function withDriveAuth<T>(operation: () => Promise<T>): Promise<T> {
  await ensureDriveAccess(); // Sets fresh token on CloudStorage
  try {
    return await operation();
  } catch (error: any) {
    // Token may have expired mid-operation
    if (error?.status === 401 || error?.message?.includes('401')) {
      const tokens = await GoogleSignin.getTokens();
      await GoogleSignin.clearCachedAccessToken(tokens.accessToken);
      await ensureDriveAccess(); // Get fresh token
      return await operation(); // Retry once
    }
    throw error;
  }
}
```

## Open Questions

1. **react-native-cloud-storage directory listing in appdata**
   - What we know: Library has `exists()` and `stat()` but directory listing API unclear for appdata scope
   - What's unclear: Whether `readdir`-equivalent exists or if we need to maintain a manifest file listing all uploaded backups
   - Recommendation: Maintain a `sync-manifest.json` in appdata that tracks all uploaded files -- avoids directory listing entirely

2. **Large file upload reliability**
   - What we know: Full backups could be 50-80MB; Drive API supports resumable uploads for files >5MB
   - What's unclear: Whether react-native-cloud-storage uses resumable upload internally or simple multipart
   - Recommendation: For v1, use simple upload via RNCS. If reliability issues surface, fall back to direct Drive REST resumable upload API for full backups only.

3. **Expo config plugin for google-signin**
   - What we know: Plugin requires `iosUrlScheme` for iOS, optional Firebase config files
   - What's unclear: Whether the Expo SDK 54 URL scheme issue (GitHub #1458) is resolved in v16.1.2
   - Recommendation: This is Android-first; iOS Google Sign-In can be tested when iOS support is added. For Android, plugin config is straightforward.
