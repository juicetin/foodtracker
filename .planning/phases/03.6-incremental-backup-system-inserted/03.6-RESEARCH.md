# Phase 3.6: Incremental Backup System - Research

**Researched:** 2026-03-19
**Domain:** SQLite change tracking, incremental backup, local file storage
**Confidence:** HIGH

## Summary

This phase implements an incremental backup system using op-sqlite's native `updateHook` for change tracking, SQLite's `VACUUM INTO` for full snapshots, and JSON changeset files for incremental diffs. The core technical challenge is minimal: op-sqlite v15.x already exposes `updateHook` with typed callbacks, `VACUUM INTO` works via standard `execute()`, and Expo's `documentDirectory` provides file storage accessible via sharing. The auto-backup scheduling uses `expo-background-task` (the modern replacement for `expo-background-fetch`) with `expo-task-manager`.

The architecture is straightforward -- a `_change_journal` table records mutations, a `backupService` exports/compacts, and the existing Profile screen gains a manual trigger button. The main pitfalls are: (1) the updateHook fires asynchronously on the JS thread so journal writes must not use `executeSync` inside the hook callback, (2) VACUUM INTO requires the target file to not exist or be empty, and (3) iOS requires `UIFileSharingEnabled` + `LSSupportsOpeningDocumentsInPlace` Info.plist keys for Files app visibility.

**Primary recommendation:** Register `updateHook` on the `opsqlite` singleton in `db/client.ts` at module load, write journal entries with `executeSync` (the hook callback runs on JS thread after the triggering operation completes), filter by a tracked-tables allowlist, and store backups in a `backups/` subdirectory of `documentDirectory`.

### Pattern 1: updateHook Registration
**What:** Register a single updateHook callback on the `opsqlite` connection that filters by tracked table names and inserts into `_change_journal`.
**When to use:** At module load time in `db/client.ts`, after table creation.
**Example:**
```typescript
// Source: op-sqlite v15.x types.d.ts (verified from installed package)
import type { UpdateHookOperation } from '@op-engineering/op-sqlite';

const TRACKED_TABLES = new Set([
  'food_entries', 'ingredients', 'photos', 'scanned_dishes',
  'favourite_meals', 'correction_history',
  'off_product_cache', 'off_search_cache', 'installed_packs',
]);

opsqlite.updateHook((params: {
  table: string;
  operation: UpdateHookOperation; // 'INSERT' | 'DELETE' | 'UPDATE'
  row?: any;
  rowId: number;
}) => {
  if (!TRACKED_TABLES.has(params.table) || params.table === '_change_journal') return;
  opsqlite.executeSync(
    'INSERT INTO _change_journal (table_name, row_id, operation, timestamp) VALUES (?, ?, ?, ?)',
    [params.table, params.rowId, params.operation, new Date().toISOString()]
  );
});
```

### Pattern 2: VACUUM INTO for Full Backup
**What:** Execute `VACUUM INTO ?` with target file path to create a clean, defragmented snapshot.
**When to use:** First backup, or compaction cycle (every 7 incrementals).
**Example:**
```typescript
// VACUUM INTO requires the target file to NOT exist
const backupPath = `${documentDirectory}backups/tastimate-backup-full-${isoDate}.db`;
await opsqlite.execute(`VACUUM INTO ?`, [backupPath]);
```

### Pattern 3: Incremental JSON Changeset Export
**What:** Read `_change_journal` entries since last backup, group by table, write as JSON with metadata header.
**When to use:** Each manual or auto-backup trigger.
**Example:**
```typescript
const changes = opsqlite.executeSync(
  'SELECT table_name, row_id, operation, timestamp FROM _change_journal ORDER BY timestamp'
).rows;

const changeset = {
  backupId: crypto.randomUUID(),
  createdAt: new Date().toISOString(),
  sinceLastBackup: lastBackupTimestamp,
  tableChangeCounts: { /* grouped counts */ },
  changes: changes, // array of {table_name, row_id, operation, timestamp}
};
```

### Pattern 4: Background Task Registration
**What:** Register a named background task at global scope for auto-backup.
**When to use:** App entry point (before React renders).
**Example:**
```typescript
import * as TaskManager from 'expo-task-manager';
import * as BackgroundTask from 'expo-background-task';

const BACKUP_TASK_NAME = 'TASTIMATE_AUTO_BACKUP';

TaskManager.defineTask(BACKUP_TASK_NAME, async () => {
  try {
    await performIncrementalBackup();
    return BackgroundTask.BackgroundTaskResult.Success;
  } catch {
    return BackgroundTask.BackgroundTaskResult.Failed;
  }
});

// Register in settings when user enables auto-backup
await BackgroundTask.registerTaskAsync(BACKUP_TASK_NAME, {
  minimumInterval: 24 * 60 * 60, // daily (OS enforces min 15 min)
});
```

### Anti-Patterns to Avoid
- **Writing to _change_journal inside a transaction boundary:** The updateHook fires for each row change; if you wrap journal inserts in their own transaction, you risk deadlocks. Use `executeSync` (single statement, auto-committed).
- **Storing full row data in the journal:** The decision explicitly says no row snapshots. The journal tracks what changed, not what the data was. Restore replays against the full backup.
- **Using VACUUM (without INTO):** Regular VACUUM rebuilds in-place and requires exclusive lock; VACUUM INTO writes to a new file without blocking reads.
- **Deleting backup files before verifying the new backup is complete:** Always write the new backup fully, verify it, then clean up old files.

## Common Pitfalls

### Pitfall 1: updateHook Fires for _change_journal Itself
**What goes wrong:** Writing to `_change_journal` inside the updateHook triggers the hook again, causing infinite recursion.
**Why it happens:** The hook fires for ALL tables on the connection.
**How to avoid:** Guard with `if (params.table === '_change_journal') return;` at the top of the callback.
**Warning signs:** Stack overflow or "maximum call stack size exceeded" errors.

### Pitfall 2: VACUUM INTO Target File Must Not Exist
**What goes wrong:** `VACUUM INTO` fails if the target file already exists and is non-empty.
**Why it happens:** SQLite requires a fresh file for VACUUM INTO output.
**How to avoid:** Delete the target file first, or use a unique timestamped filename (which the naming convention already ensures).
**Warning signs:** "output file already exists" SQLite error.

### Pitfall 3: VACUUM INTO Output Uses DELETE Journal Mode
**What goes wrong:** The backup .db file does not inherit WAL mode from the source database.
**Why it happens:** VACUUM INTO creates a new database with default journal_mode (DELETE), not WAL.
**How to avoid:** This is actually desirable for backup files -- DELETE mode means the backup is a single self-contained .db file (no -wal or -shm companions).
**Warning signs:** None -- this is the correct behavior for portable backup files.

### Pitfall 4: iOS Files App Requires Info.plist Keys
**What goes wrong:** Backup files in documentDirectory are not visible in iOS Files app.
**Why it happens:** iOS requires `UIFileSharingEnabled` and `LSSupportsOpeningDocumentsInPlace` in Info.plist.
**How to avoid:** Add these keys via Expo config plugin or app.json `ios.infoPlist`.
**Warning signs:** Files saved successfully but invisible to user in Files app.

### Pitfall 5: Background Task Minimum Interval
**What goes wrong:** Auto-backup doesn't run as frequently as configured.
**Why it happens:** Both iOS (BGTaskScheduler) and Android (WorkManager) enforce a minimum 15-minute interval, and actual scheduling is OS-discretionary.
**How to avoid:** Accept that "daily" is a target, not a guarantee. The OS may defer the task based on battery, network, and usage patterns. Default to daily interval (86400 seconds).
**Warning signs:** Tasks running less frequently than expected -- this is normal OS behavior.

### Pitfall 6: Compaction Replay Order Matters
**What goes wrong:** Replaying incremental diffs in wrong order produces inconsistent state.
**Why it happens:** If incrementals are applied out of chronological order, later deletes may be followed by earlier inserts.
**How to avoid:** Sort incremental files by timestamp before replay. Include sequence number in metadata.
**Warning signs:** Foreign key violations or duplicate key errors during compaction.

CREATE TABLE IF NOT EXISTS _change_journal (
  id INTEGER PRIMARY KEY AUTOINCREMENT,

  journal_from TEXT,  -- earliest journal timestamp included

## Open Questions

1. **Compaction replay without row data in journal**
   - What we know: The journal only stores table_name, row_id, operation, timestamp -- no row data
   - What's unclear: Compaction needs to "replay" changes onto a full backup, but the journal has no data to replay. The actual replay must query current live DB state for each row_id.
   - Recommendation: Compaction should query the live database for current row state (for INSERT/UPDATE) and apply DELETE directly. This means compaction produces a snapshot of current state, not a historical replay. This is equivalent to just doing another VACUUM INTO -- consider whether compaction should simply be another full backup (VACUUM INTO) rather than a journal replay.

2. **expo-background-task availability**
   - What we know: It's the modern replacement, available from SDK 53+
   - What's unclear: Whether it's bundled with SDK 54 or requires separate install
   - Recommendation: Check with `npx expo install expo-background-task expo-task-manager` which will resolve correct versions

3. **Android file visibility**
   - What we know: documentDirectory is app-sandboxed on Android; files are accessible via file manager apps that can browse app data
   - What's unclear: Whether Android users can easily find backup files without SAF picker
   - Recommendation: Use expo-sharing to offer a share/export action alongside direct file storage; this covers both platforms
