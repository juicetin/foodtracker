# Phase 3.6: Incremental Backup System - Context

**Gathered:** 2026-03-19
**Status:** Ready for planning

<domain>
## Phase Boundary

Incremental backup system for all user data. op-sqlite updateHook writes a change journal tracking every INSERT/UPDATE/DELETE. Manual or automatic backup trigger exports journal entries as JSON changeset files (incremental diffs). Periodic VACUUM INTO creates full .db snapshots. Compaction replays incremental diffs onto a full backup to produce a merged snapshot. Backup files stored on local device storage accessible via Files app.

</domain>

<decisions>
## Implementation Decisions

### Change journal
- op-sqlite `updateHook` writes to a `_change_journal` table for every INSERT/UPDATE/DELETE on user-data tables
- Tracked tables: food_entries, ingredients, photos, scanned_dishes, favourite_meals, correction_history, off_product_cache, off_search_cache, installed_packs
- Journal columns: table_name, rowid, operation (INSERT/UPDATE/DELETE), timestamp
- Journal does NOT store row data snapshots — it records what changed; restore replays against the full backup
- Journal is ephemeral — cleared after successful backup export

### Backup trigger & scheduling
- Both manual and automatic backups supported
- Manual trigger available in Profile/Settings screen
- Auto-backup on configurable interval, default daily
- Manual backup runs in foreground with progress indicator
- Auto-backup runs in background silently

### File format & storage
- Incremental backups: JSON changeset file with metadata header (backup ID, timestamp, since-last-backup timestamp, table change counts)
- Full backups: VACUUM INTO producing a clean, portable .db snapshot
- Storage location: app's document directory accessible via Files app (iOS) / file manager (Android)
- File naming: `tastimate-backup-full-{ISO-date}.db` and `tastimate-backup-incremental-{ISO-date}.json`

### Compaction & retention
- Compaction triggered after 7 incremental backups (aligned with daily auto-backup = weekly compaction)
- Compaction replays incremental JSON diffs onto the last full backup to produce a merged full backup
- Retain last 3 full backups; delete older full backups and their associated incrementals
- Compaction produces a new full backup file, does not modify the source

### Claude's Discretion
- Exact updateHook registration and lifecycle management
- JSON changeset internal structure beyond the metadata header
- Progress indicator implementation for manual backup
- Whether to show backup size/count in Settings UI
- Error handling and retry logic for failed backups

</decisions>

<specifics>
## Specific Ideas

- User said (Phase 3.5): "make sure that our full backups of all user data includes these caches" — OFF cache must be in backups
- Backup must be self-contained: a full .db snapshot can be opened independently with any SQLite client
- VACUUM INTO chosen over raw file copy because it produces a clean, defragmented snapshot even during active use

</specifics>
