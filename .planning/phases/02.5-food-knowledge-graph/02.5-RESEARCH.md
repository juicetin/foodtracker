# Phase 2.5: Food Knowledge Graph - Research

**Researched:** 2026-03-14
**Domain:** On-device food knowledge graph (SQLite), recipe-based nutrition decomposition, fuzzy text search
**Confidence:** HIGH

## Summary

This phase builds a compact on-device food knowledge graph in SQLite that replaces the hardcoded flat-rate nutrition proxies (1.5 kcal/g, 0.1 protein/g, 0.2 carbs/g, 0.08 fat/g) in DetectionScreen.tsx with recipe-based nutrition decomposition. The core flow is: YOLO className -> KG dish lookup (FTS5 + SymSpell fuzzy match) -> canonical recipe -> ingredient-level USDA nutrition -> aggregated portion-scaled macros.

The existing codebase already has substantial infrastructure: a Python pipeline (`knowledge-graph/`) with schema.sql, seed_recipenlg.py, seed_usda.py, generate_dishes.py, query.py, and export_mobile.py -- but the current schema is flat (dishes, ingredients, dish_ingredients) and the food-knowledge.db is 0 bytes (nothing seeded yet). The mobile side has NutritionService, RegionalResolver, and PackManager that handle nutrition DB packs, but no KG-specific service exists. The `installed_packs` table currently accepts type 'nutrition' | 'model' and needs a new 'knowledge-graph' type.

**Primary recommendation:** Restructure the Python schema from flat to hierarchical (cuisine -> dish_category -> dish -> recipe -> recipe_ingredient -> usda_food), seed from RecipeNLG + generate_dishes.py + WorldCuisines aliases, build a TypeScript KnowledgeGraphService on mobile with SymSpell fuzzy matching, and wire it into DetectionScreen to replace the hardcoded macro constants.

```sql
  id INTEGER PRIMARY KEY,
  dish_id INTEGER REFERENCES dish(id),
```

### Pattern 2: Nutrition Decomposition Pipeline

**What:** The core KG query flow from className to macros
**When to use:** Every time a detected food item needs nutrition data

```typescript
// KnowledgeGraphService pattern
async function calculateDishNutrition(
  className: string,
  portionGrams: number
): Promise<MacroResult | null> {
  // 1. Search dish by className (FTS5 + SymSpell fallback)
  const dish = await searchDish(className);
  if (!dish) return null;

  // 2. Get canonical recipe
  const recipe = await getCanonicalRecipe(dish.id);
  if (!recipe) {
    // Fallback to per-dish averages
    return scaleMacros(dish, portionGrams);
  }

  // 3. Get recipe ingredients with USDA nutrition
  const ingredients = await getRecipeIngredients(recipe.id);

  // 4. Sum per-ingredient nutrition, scale to portion
  let totalCal = 0, totalProtein = 0, totalCarbs = 0, totalFat = 0;
  for (const ing of ingredients) {
    if (!ing.usdaFdcId || !ing.quantityGrams) continue;
    const usda = await getUsdaFood(ing.usdaFdcId);
    if (!usda) continue;
    const scale = ing.quantityGrams / 100;
    totalCal += usda.caloriesPer100g * scale;
    totalProtein += usda.proteinPer100g * scale;
    totalCarbs += usda.carbsPer100g * scale;
    totalFat += usda.fatPer100g * scale;
  }

  // 5. Scale from recipe total to requested portion
  const recipeWeight = recipe.totalWeightGrams ||
    ingredients.reduce((s, i) => s + (i.quantityGrams || 0), 0);
  const portionScale = portionGrams / (recipeWeight / (recipe.servings || 1));

  return {
    calories: Math.round(totalCal * portionScale / (recipe.servings || 1)),
    protein: Math.round(totalProtein * portionScale / (recipe.servings || 1) * 10) / 10,
    carbs: Math.round(totalCarbs * portionScale / (recipe.servings || 1) * 10) / 10,
    fat: Math.round(totalFat * portionScale / (recipe.servings || 1) * 10) / 10,
    weightGrams: portionGrams,
  };
}
```

### Pattern 4: Pack Type Extension

**What:** Add 'knowledge-graph' as a valid pack type
**When to use:** When registering the KG database with PackManager

The `installed_packs` table uses `type TEXT NOT NULL` -- no enum constraint, so adding 'knowledge-graph' requires:
1. Update TypeScript type union: `type: 'nutrition' | 'model' | 'knowledge-graph'`
2. Update PackEntry/InstalledPack interfaces in `packs/types.ts`
3. RegionalResolver already filters `p.type === 'nutrition'` so KG packs won't conflict
4. KnowledgeGraphService opens its own db connection (same pattern as NutritionService)

### Anti-Patterns to Avoid

- **Cross-DB JOINs at runtime:** Do NOT query the existing USDA nutrition pack DB from KnowledgeGraphService. Embed the needed USDA SR Legacy macros (just 7 columns: fdc_id, description, calories, protein, fat, carbs, fiber) directly in the KG's `usda_food` table. This keeps the KG self-contained and avoids runtime dependency on whether USDA packs are installed.
- **Loading full SymSpell dictionary on app start:** Pre-compute the SymSpell dictionary at KG build time in Python. Ship it as a JSON blob or SQLite table in the KG database. Load lazily on first search, not at app boot.
- **Modifying the user DB schema for KG data:** The KG is a read-only reference database (like nutrition packs). Do NOT add KG tables to the user drizzle schema.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Fuzzy string matching | Edit distance loop over all dishes | SymSpell pre-computed deletes | O(1) lookup vs O(n) scan; 1,870x faster per research |
| Full-text search | LIKE '%query%' on all dishes | FTS5 with BM25 ranking | Built into SQLite, handles tokenization, ranking, prefix matching |
| Ingredient-to-USDA mapping | Runtime NLP/NER parsing | Pre-computed mapping table in KG | Ship static mappings; runtime NER is overkill for canonical recipes |
| Recipe portion normalization | Manual unit conversion at runtime | Pre-normalize all quantities to grams in Python pipeline | Eliminate "2 cups" -> grams conversion on device; do it once during build |
| CSV/JSON recipe parsing on device | Parse RecipeNLG on mobile | Pre-process in Python, ship as SQLite | Mobile should only query pre-built SQLite |

**Key insight:** All data transformation and normalization happens in the Python build pipeline. The mobile app only opens and queries a pre-built, pre-optimized SQLite database. This matches the existing pattern used for USDA nutrition packs.

## Common Pitfalls

### Pitfall 1: seed_usda.py Bug (Lines 360-361)
**What goes wrong:** Lines 360-364 use bare variable names (`api_calls`, `dishes_updated`, `dishes_created`, `fdc_ids_set`, `ingredients_mapped`) instead of `counters["key"]` in the print statements. The function uses a `counters` dict everywhere else.
**Why it happens:** Copy-paste from an earlier version that used individual variables.
**How to avoid:** Fix lines 360-364 to use `counters["api_calls"]`, `counters["dishes_updated"]`, etc.
**Warning signs:** `NameError` when running `seed_usda.py` to completion.

### Pitfall 2: RecipeNLG Recipe Deduplication
**What goes wrong:** RecipeNLG has 2.2M recipes, many duplicates. Without deduplication, the KG balloons in size.
**Why it happens:** `normalize_dish_name()` in seed_recipenlg.py does basic normalization but many near-duplicates survive (e.g., "fried rice recipe", "easy fried rice", "quick fried rice" all normalize differently).
**How to avoid:** After normalization, aggregate by dish name (existing code does this), then filter to dishes with >= 3 recipe occurrences for confidence. Cap at 5K-10K most common dishes.
**Warning signs:** KG exceeds 70MB size budget or has >50K dishes (most being obscure single-recipe entries).

### Pitfall 3: YOLO Class Names vs KG Dish Names
**What goes wrong:** YOLO returns class names like "Airan Katyk" or "Pad Thai" (formatted by `formatFoodLabel()`), but KG dishes are stored as lowercase normalized names like "pad thai". Search fails silently.
**Why it happens:** The detection pipeline title-cases all names via `formatFoodLabel()`.
**How to avoid:** KnowledgeGraphService.searchDish() must normalize input to lowercase before FTS5/SymSpell query. Also store YOLO class names as dish_aliases in the KG for direct matching.
**Warning signs:** KG returns null for detected items despite having the dish in the database.

### Pitfall 4: FTS5 Content Sync Triggers
**What goes wrong:** FTS5 `content=` tables require explicit triggers to stay in sync. Missing a trigger means inserts/updates don't appear in search.
**Why it happens:** The existing schema.sql has triggers for `dishes_fts` but the new schema needs separate triggers for `dish_fts` and `dish_alias_fts`.
**How to avoid:** Always create AFTER INSERT/DELETE/UPDATE triggers when using `content=` FTS5 tables. The existing triggers in schema.sql are the correct pattern.
**Warning signs:** Data appears in direct table queries but not in FTS5 MATCH queries.

### Pitfall 5: KG Pack Schema Validation Conflict
**What goes wrong:** RegionalResolver's `validatePackSchema()` checks for nutrition-specific tables (foods, nutrients, food_nutrients, food_portions, foods_fts). A KG pack would fail this validation.
**Why it happens:** The existing validation is nutrition-schema-specific.
**How to avoid:** KG packs use type='knowledge-graph', not type='nutrition'. KnowledgeGraphService opens the DB directly (same as NutritionService), bypassing RegionalResolver entirely. Do NOT route KG through RegionalResolver.
**Warning signs:** "Custom pack schema validation failed" errors when trying to install KG.

### Pitfall 6: WorldCuisines Dataset Format
**What goes wrong:** Treating WorldCuisines food-kb as a simple name-translation table when it's actually a structured dataset with nested fields (aliases as text, cuisines/areas as lists).
**Why it happens:** The dataset has 2,410 rows with complex column types (lists for cuisines, areas, countries).
**How to avoid:** Use the HuggingFace `datasets` library to load it properly. Extract: `name` -> dish canonical name, `alias` -> pipe-delimited or comma-delimited aliases (parse carefully), `cuisines` -> cuisine tags, `area` -> geographic region.
**Warning signs:** Missing aliases or garbled Unicode in multilingual names.

### SymSpell Index Initialization (TypeScript)

```typescript
// Pattern for loading SymSpell dictionary from KG database
// Source: SymSpell algorithm (https://github.com/wolfgarbe/SymSpell)

interface SymSpellMatch {
  term: string;
  distance: number;
  dishId: number;
}

class SymSpellIndex {
  private deleteDict: Map<string, number[]> = new Map(); // delete variant -> dish IDs
  private terms: Map<number, string> = new Map(); // dish ID -> canonical name
  private maxEditDistance = 2;

  /** Load dictionary from pre-computed table in KG database */
  async loadFromDb(db: OPSQLiteConnection): Promise<void> {
    // Option A: Pre-computed deletes stored in KG
    const result = await db.execute(
      'SELECT dish_id, delete_variant FROM symspell_deletes'
    );
    for (const row of result.rows) {
      const variant = row.delete_variant as string;
      const dishId = row.dish_id as number;
      const existing = this.deleteDict.get(variant) || [];
      existing.push(dishId);
      this.deleteDict.set(variant, existing);
    }

    // Load terms
    const dishes = await db.execute('SELECT id, canonical_name FROM dish');
    for (const row of dishes.rows) {
      this.terms.set(row.id as number, row.canonical_name as string);
    }
  }

  /** Find closest matches for a query term */
  lookup(query: string, maxResults = 5): SymSpellMatch[] {
    const queryLower = query.toLowerCase().trim();
    const candidates: Map<number, number> = new Map(); // dishId -> distance

    // Generate deletes of the query
    const queryDeletes = this.generateDeletes(queryLower, this.maxEditDistance);
    queryDeletes.add(queryLower); // include the query itself

    for (const variant of queryDeletes) {
      const dishIds = this.deleteDict.get(variant);
      if (!dishIds) continue;
      for (const dishId of dishIds) {
        if (candidates.has(dishId)) continue;
        const term = this.terms.get(dishId) || '';
        const dist = this.editDistance(queryLower, term);
        if (dist <= this.maxEditDistance) {
          candidates.set(dishId, dist);
        }
      }
    }

    return Array.from(candidates.entries())
      .map(([dishId, distance]) => ({
        term: this.terms.get(dishId) || '',
        distance,
        dishId,
      }))
      .sort((a, b) => a.distance - b.distance)
      .slice(0, maxResults);
  }

  private generateDeletes(word: string, maxDist: number): Set<string> {
    const deletes = new Set<string>();
    if (word.length <= 1) return deletes;

    const queue = [{ word, dist: 0 }];
    while (queue.length > 0) {
      const { word: w, dist } = queue.shift()!;
      if (dist >= maxDist) continue;
      for (let i = 0; i < w.length; i++) {
        const del = w.slice(0, i) + w.slice(i + 1);
        if (!deletes.has(del)) {
          deletes.add(del);
          queue.push({ word: del, dist: dist + 1 });
        }
      }
    }
    return deletes;
  }

  private editDistance(a: string, b: string): number {
    // Damerau-Levenshtein distance
    const m = a.length, n = b.length;
    const dp: number[][] = Array.from({ length: m + 1 }, () => Array(n + 1).fill(0));
    for (let i = 0; i <= m; i++) dp[i][0] = i;
    for (let j = 0; j <= n; j++) dp[0][j] = j;
    for (let i = 1; i <= m; i++) {
      for (let j = 1; j <= n; j++) {
        const cost = a[i-1] === b[j-1] ? 0 : 1;
        dp[i][j] = Math.min(dp[i-1][j] + 1, dp[i][j-1] + 1, dp[i-1][j-1] + cost);
        if (i > 1 && j > 1 && a[i-1] === b[j-2] && a[i-2] === b[j-1]) {
          dp[i][j] = Math.min(dp[i][j], dp[i-2][j-2] + cost);
        }
      }
    }
    return dp[m][n];
  }
}
```

### KG Database Open Pattern (TypeScript)

```typescript
// Follows the same pattern as NutritionService.open() / RegionalResolver
import { openNutritionDb } from '../../../db/client';

export class KnowledgeGraphService {
  private db: ReturnType<typeof openNutritionDb> | null = null;
  private symspell: SymSpellIndex | null = null;

  async open(dbPath: string): Promise<void> {
    this.db = openNutritionDb(dbPath); // reuse same op-sqlite open function
    this.symspell = new SymSpellIndex();
    await this.symspell.loadFromDb(this.db);
  }

  async searchDish(query: string): Promise<DishResult | null> {
    const db = this.getDb();
    const normalized = query.toLowerCase().replace(/[-_]/g, ' ').trim();

    // 1. Try FTS5 first
    const ftsResult = await db.execute(
      `SELECT d.id, d.canonical_name, d.avg_calories_per_serving,
              d.default_serving_grams
       FROM dish_fts
       JOIN dish d ON d.id = dish_fts.rowid
       WHERE dish_fts MATCH ?
       LIMIT 1`,
      [normalized + '*']
    );
    if (ftsResult.rows.length > 0) return mapDish(ftsResult.rows[0]);

    // 2. Try alias FTS5
    const aliasResult = await db.execute(
      `SELECT d.id, d.canonical_name, d.avg_calories_per_serving,
              d.default_serving_grams
       FROM dish_alias_fts
       JOIN dish_alias da ON da.id = dish_alias_fts.rowid
       JOIN dish d ON d.id = da.dish_id
       WHERE dish_alias_fts MATCH ?
       LIMIT 1`,
      [normalized + '*']
    );
    if (aliasResult.rows.length > 0) return mapDish(aliasResult.rows[0]);

    // 3. SymSpell fuzzy match
    if (this.symspell) {
      const matches = this.symspell.lookup(normalized, 1);
      if (matches.length > 0) {
        return this.getDishById(matches[0].dishId);
      }
    }

    return null;
  }
}
```

## Open Questions

1. **RecipeDB Access Method**
   - What we know: RecipeDB has 118K recipes across 74 countries with USDA-linked ingredients. License is CC-BY-NC-SA 3.0 (non-commercial OK). Companion GitHub repo only has NER training data, not full recipe data.
   - What's unclear: Whether RecipeDB provides bulk download or requires scraping their API. The website (cosylab.iiitd.edu.in/recipedb) may require registration.
   - Recommendation: Use RecipeNLG (2.2M recipes, already integrated via seed_recipenlg.py) + generate_dishes.py (1000+ curated) as primary sources. If RecipeDB bulk data is easily obtainable, use it to enrich ingredient-to-USDA mappings. Don't block on RecipeDB access.

2. **WorldCuisines Alias Field Format**
   - What we know: The `alias` field is TEXT type, 2-1,010 characters. Contains multilingual names.
   - What's unclear: Exact delimiter format (comma, pipe, newline, or structured). Need to inspect actual data rows.
   - Recommendation: Load the dataset in Python and inspect first 10 rows of the `alias` column to determine parsing strategy.

3. **NUT-01 Requirement Definition**
   - What we know: Referenced in ROADMAP as a requirement for Phase 2.5 but not defined in REQUIREMENTS.md.
   - What's unclear: Exact acceptance criteria.
   - Recommendation: Treat NUT-01 as "detection pipeline produces per-dish nutrition from knowledge graph instead of hardcoded flat-rate proxies." This is clearly the intent from the phase description and CONTEXT.md.

4. **SymSpell Pre-computation Storage**
   - What we know: SymSpell needs a dictionary of delete variants. For 10K dishes at max edit distance 2, this could be ~50K-100K delete entries.
   - What's unclear: Whether to store as a SQLite table in the KG or as a JSON file.
   - Recommendation: Store as a SQLite table (`symspell_deletes`) in the KG database. Consistent with the single-file pack pattern. Pre-compute during the Python build pipeline.
