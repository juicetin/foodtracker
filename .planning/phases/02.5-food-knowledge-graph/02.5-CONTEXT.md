# Phase 2.5: Food Knowledge Graph — Context

## What This Phase Does

Builds a compact on-device food knowledge graph (SQLite, <70MB) that enables recipe-based nutrition decomposition. Instead of the current hardcoded 1.5 kcal/g proxy, detected foods are looked up in the KG → canonical recipe found → ingredients mapped to USDA nutrition → real macros calculated.

## Why It Matters

The detection pipeline currently identifies food (YOLO 241 classes) but has no real nutrition data. DetectionScreen.tsx lines 321-325 use `KCAL_PER_GRAM = 1.5` for everything. This phase bridges detection → nutrition.

## Existing Infrastructure (What's Already Built)

### knowledge-graph/ Python Pipeline
- `schema.sql` — flat schema (dishes, ingredients, dish_ingredients) with FTS5. Needs restructuring for the hierarchical target schema.
- `seed_recipenlg.py` (782 lines) — ingests RecipeNLG 2.2M recipes from HuggingFace. Parses ingredients, classifies cuisines.
- `generate_dishes.py` (1319 lines) — programmatic fallback generating 1000+ curated dishes with hardcoded ingredient profiles.
- `seed_usda.py` (397 lines) — enriches from USDA FDC API. **Bug on lines 360-361**: bare variables instead of `counters["key"]`.
- `build_usda_db.py`, `build_regional_db.py` — proven SQLite build pipelines for nutrition packs.
- `export_mobile.py` (178 lines) — WAL checkpoint, DELETE mode, VACUUM, copy to mobile. Has 50MB size check.
- `query.py` (412 lines) — Python query API: get_ingredients, search_dish, get_variants, get_best_guess.
- `food-knowledge.db` is **0 bytes** — nothing seeded yet.
- Requirements: requests, tqdm, datasets, pandas, openpyxl, pytest.

### Mobile Nutrition System
- `nutritionSchema.ts` — published schema: foods, nutrients, food_nutrients, food_portions, foods_fts.
- `NutritionService` — searchFoods (FTS5), getFoodById, getFoodNutrients, getMacros (scales per-100g to weight).
- `RegionalResolver` — multi-DB query router. Priority: regional > usda-core > usda-branded > custom.
- `PackManager` — generic pack download/install/verify. Can be reused for KG pack.
- `validatePackSchema()` in RegionalResolver checks for nutrition schema — KG schema would fail validation. Needs new pack type.

### User DB Recipe Tables (separate from KG)
- `custom_recipes`, `recipe_ingredients`, `recipe_photos` — for user-created recipes, not KG canonical recipes.

### Detection Pipeline Integration Points
- `inferenceRouter.ts` returns `DetectedItem[]` with `className` and `confidence`.
- `portionBridge.ts` produces `weightG` estimate.
- `DetectionScreen.tsx` uses hardcoded flat-rate proxies for macros. This is the replacement target.

## Target Schema (from research)

```sql
cuisine (id, name, region)
dish_category (id, cuisine_id, name, parent_id)  -- hierarchical
dish (id, category_id, canonical_name, avg_calories_per_serving, avg_protein/carbs/fat, default_serving_grams)
dish_alias (id, dish_id, alias, language, alias_type)  -- multilingual, spelling variants
recipe (id, dish_id, name, source, total_calories, total_weight_grams, servings, is_canonical)
recipe_ingredient (id, recipe_id, usda_food_id, ingredient_name, quantity, unit, quantity_grams)
dish_fts (FTS5 on canonical_name, description)
dish_alias_fts (FTS5 on alias)
```

## Data Sources

**RecipeDB licensing caveat**: Research-licensed. May need to build curated set from public-domain sources instead.

## Key Decisions Already Made (from research discussion)

1. Plain SQLite with JOINs — no graph DB extension needed (food KG queries are 2-3 hop joins)
2. SymSpell for typo-tolerant fuzzy matching (1,870x faster than BK-tree)
3. FTS5 for full-text search (already used in nutrition DBs)
4. Recipe-based decomposition: dish → recipe → ingredients → USDA nutrition → aggregate
5. Size budget: 40-70 MB total on device
6. Fallback chain: KG recipe decomposition → KG per-dish averages → flat-rate proxy
