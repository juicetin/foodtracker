  <action>
    1. **Add `.db` to Metro assetExts** in `apps/mobile/metro.config.js`:
       - Add `config.resolver.assetExts.push('db');` after the existing `tflite` push
       - This is required for Metro to bundle `.db` files as assets (documented in .planning/research/PITFALLS.md)
       - Without this, the database silently fails to bundle in production builds

    2. **Copy food-knowledge.db to bundled assets directory**:
       - Place the built food-knowledge.db at `apps/mobile/assets/data/food-knowledge.db`
       - This follows the same convention as `assets/models/*.tflite` for bundled ML models
       - The file must exist before the APK build (Plan 01's export_mobile.py should output here, or copy manually after build)
       - Delivery decision: **bundle in APK** (not downloadable pack). Rationale: the KG is under 70MB (target 40-60MB after VACUUM), every user needs it for basic nutrition, and bundling avoids a mandatory first-run download. This is the same pattern used for bundled .tflite models. If future KG versions exceed 100MB, revisit and switch to PackManager downloadable pack.

    3. **Create knowledgeGraphProvider.ts** -- lazy singleton for KG service:
       - Export `getKnowledgeGraphService()`: returns singleton KnowledgeGraphService instance
       - On first call, creates instance, calls `open()` with the resolved path to the bundled food-knowledge.db
       - Resolve the bundled DB path using `require('../../assets/data/food-knowledge.db')` -- this returns a numeric asset ID at build time. Use `Asset.fromModule(assetId).downloadAsync()` from `expo-asset` to get the local URI, then pass `asset.localUri` to `open()`. This is the standard Expo pattern for accessing bundled binary assets that need a filesystem path (unlike .tflite which are loaded by a native module that handles asset IDs directly).
       - Catches open errors gracefully (if KG DB not found or asset resolution fails, log warning via console.warn and return null -- detection still works with flat-rate proxy)
       - NOT loaded at app boot -- only when first detection flow needs nutrition
       - Cache the resolved path after first resolution to avoid repeated Asset.downloadAsync calls

    4. **Create index.ts** barrel export:
       - Re-export KnowledgeGraphService, MacroResult, DishResult from knowledgeGraphService.ts
       - Re-export getKnowledgeGraphService from knowledgeGraphProvider.ts
       - Re-export SymSpellIndex from symspellIndex.ts

    5. **Update DetectionScreen.tsx**:
       a. Remove the flat-rate proxy constants (KCAL_PER_GRAM, PROTEIN_PER_GRAM, CARB_PER_GRAM, FAT_PER_GRAM)
       b. Import `getKnowledgeGraphService` and `MacroResult` from the knowledge-graph barrel
       c. Create a helper function `getNutritionForItem(item: DetectedItem)` that implements the three-tier fallback chain:
          - Tier 1: `kgService.calculateDishNutrition(item.className, weightG)` -- returns MacroResult with source='recipe' if KG has recipe
          - Tier 2: `kgService.getDishAverages(item.className)` -- returns MacroResult with source='dish_average' if KG has dish-level averages but no recipe
          - Tier 3: flat-rate proxy calculation (weightG * 1.5 for cal, etc.) -- returns MacroResult with source='proxy'
          - If kgService is null (DB not found), go straight to Tier 3
       d. Replace the logging loop (lines ~321-327) to use `getNutritionForItem()` for each detected item:
          - The loop becomes async: `for (const item of currentActive) { const macros = await getNutritionForItem(item); totalCal += macros.calories; ... }`
          - This is acceptable performance-wise because KG queries are local SQLite (<5ms each)
       e. Add `__DEV__` logging: for each item, log which tier was used (recipe/dish_average/proxy) and the macro values
       f. Keep the flat-rate proxy values as the Tier 3 fallback (not removed, just moved into the fallback function)
