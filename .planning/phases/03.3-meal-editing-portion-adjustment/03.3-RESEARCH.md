# Phase 03.3: Meal Editing + Portion Adjustment - Research

**Researched:** 2026-03-21
**Domain:** React Native meal editing UI, real-time nutrition recalculation, Gemini Nano re-identification
**Confidence:** HIGH

## Summary

Phase 03.3 builds the correction/refinement layer on top of the existing diary. The EntryDetailScreen already has a working edit mode with inline weight editing, ingredient add/remove, dish rename, and recalculation. The entryEditorService provides all the CRUD primitives. Phase 3.2 built KG + OFF search for adding ingredients. Gemini Nano identification is available via geminiNanoService.identify().

The main new work is: (1) serving size selector with KG standard portions + free-form gram input, (2) ingredient search via KG/OFF when adding new ingredients (reusing FoodSearchScreen patterns), (3) diff/merge UI for Gemini Nano re-identification, (4) undo/redo stack for edit sessions, and (5) photo viewing for UI-07.

**Primary recommendation:** Extend the existing EntryDetailScreen edit mode rather than building a separate screen. Use command pattern for undo/redo (lightweight, fits the "few ingredients" scope). Build the diff/merge re-identification view as a full-screen modal stacked on top of EntryDetail.

### Pattern 1: Command Pattern for Undo/Redo
**What:** Each edit operation (weight change, add, remove, rename, drag between sides) is wrapped in a Command object with execute() and undo() methods. A stack tracks commands for undo/redo.
**When to use:** User indicated "full undo/redo stack until Save+Confirm" but scope is limited (few ingredients per meal).
**Example:**
```typescript
interface EditCommand {
  execute(): void;
  undo(): void;
  description: string;
}

interface EditSession {
  commands: EditCommand[];
  pointer: number; // index of last executed command
  snapshotBeforeEdit: EntrySnapshot; // for Reset button
}

// Weight change command
class ChangeWeightCommand implements EditCommand {
  constructor(
    private ingredientId: string,
    private oldAmountG: number,
    private newAmountG: number,
  ) {}
  execute() { updateIngredientWeight(this.ingredientId, this.newAmountG); }
  undo() { updateIngredientWeight(this.ingredientId, this.oldAmountG); }
  description = 'Change weight';
}
```

**Why command pattern over state snapshots:** State snapshots would require serializing/deserializing full entry state on each edit. Command pattern is simpler for the small number of operations (weight, add, remove, rename, move between sides). Each command is a thin wrapper around existing entryEditorService functions.

### Pattern 2: Real-Time Recalculation
**What:** Every ingredient edit triggers recalculateEntryTotals() immediately, then reloads the entry state.
**When to use:** User locked decision: "not batch on Save."
**Implementation:** The existing EntryDetailScreen already does this pattern -- handleWeightChange calls updateIngredientWeight + recalculateEntryTotals + reload. The pattern scales fine for a meal's worth of ingredients (typically 3-15 items, one SQL SUM query).

### Pattern 3: Diff/Merge for Re-identification
**What:** When user taps "Re-scan with Gemini Nano":
1. Call geminiNanoService.identify(photoUri) to get new VlmFoodResult
2. Enrich new result through KG pipeline (same as initial scan)
3. Present side-by-side: left = current ingredients, right = new Gemini results
4. User drags items between sides (keep/discard)
5. Save+Confirm applies final state, Reset returns to pre-scan state

**Implementation approach:**
- Full-screen modal (not bottom sheet) -- diff/merge needs screen real estate
- Two FlatList columns side by side
- Gesture.Pan on each item for drag-and-drop between columns
- Animated placeholder shows drop target
- Items in "keep" column (right) will be persisted on Save
- Reset restores the snapshot taken before re-identification started

### Pattern 4: Ingredient Search When Adding
**What:** When user taps "Add Ingredient" in edit mode, open a bottom sheet with KG/OFF search (reusing the search logic from FoodSearchScreen).
**Why bottom sheet:** Keeps the edit context visible behind the sheet. User can see the dish they're editing while searching.
**Implementation:** Extract search logic from FoodSearchScreen into a reusable hook (useIngredientSearch), then use it in both FoodSearchScreen and IngredientSearchSheet.

### Anti-Patterns to Avoid
- **Editing in a separate screen copy:** Don't duplicate EntryDetailScreen for edit mode. The existing screen already toggles read/edit mode. Extend it.
- **Storing nutrition in VLM output format:** VLM returns raw ingredient names + weights. Always enrich through KG before displaying or persisting. Don't show un-enriched VLM data as nutrition.
- **Optimistic UI without DB write:** The existing pattern is write-to-SQLite-then-reload. Don't introduce optimistic Zustand-only state that diverges from DB. Keep DB as source of truth.

## Common Pitfalls

### Pitfall 1: Gesture Conflicts Between Drag and Scroll
**What goes wrong:** Drag-and-drop on items inside a ScrollView/FlatList causes scroll and drag to fight.
**Why it happens:** Both gestures respond to vertical pan.
**How to avoid:** Use Gesture.Pan() with activeOffsetX (horizontal drag threshold) on draggable items, and failOffsetY on the parent scroll. The project already uses this pattern in DiaryScreen for swipe gestures (noted in STATE.md: "Gesture.Pan with activeOffsetX/failOffsetY prevents swipe from hijacking vertical scroll").
**Warning signs:** Items won't drag, or list won't scroll when edit mode is active.

### Pitfall 2: Stale Nutrition After Weight Recalculation
**What goes wrong:** Displayed nutrition doesn't match DB after rapid weight changes.
**Why it happens:** Multiple rapid weight changes trigger multiple recalculateEntryTotals calls. If reload is async but state updates are batched, intermediate state can flash.
**How to avoid:** Debounce weight input changes (300-500ms) before calling updateIngredientWeight + recalculate. The input can show the typed value immediately while DB write is debounced.
**Warning signs:** Nutrition numbers flickering or showing wrong values during rapid slider movement.

### Pitfall 3: Re-identification With No Photo
**What goes wrong:** User taps re-scan on a manually-added entry that has no photo.
**Why it happens:** Not all entries have photos (quick-add, manual search entries).
**How to avoid:** Check entry.photoUri before showing re-scan button. Hide the button and show "No photo available for re-scan" if null. This is a Claude's Discretion item.

### Pitfall 4: Undo After Save
**What goes wrong:** User expects undo to work after pressing Save.
**Why it happens:** Save commits to DB and clears the undo stack.
**How to avoid:** Clear undo stack on Save+Confirm. Make Save explicitly final with a confirmation if there's a complex merge in progress.

### Pitfall 5: Original Amount Baseline Corruption
**What goes wrong:** After editing weight, original_amount_g gets overwritten, breaking proportional nutrition scaling.
**Why it happens:** If addIngredient sets original_amount_g = amount_g, then user edits weight, the scaling baseline shifts.
**How to avoid:** Never update original_amount_g during edit. The existing entryEditorService.updateIngredientWeight correctly reads original_amount_g and only updates amount_g. Maintain this invariant.

## Open Questions

1. **Photo zoom library**
   - What we know: Need tap-to-zoom for UI-07. react-native-image-viewing is common but may need checking if it's compatible with current RN/Expo version.
   - What's unclear: Whether to install a new package or build minimal zoom with reanimated (already installed).
   - Recommendation: Use reanimated's pinchGesture + panGesture for a lightweight zoom view. Avoids adding a dependency for a single use case. If too complex, install react-native-image-viewing.

2. **Multiple photos per entry**
   - What we know: Schema supports multiple photos per entry (photos table has entry_id FK). Current loadEntry() uses LIMIT 1.
   - What's unclear: Whether UI-07 means viewing ALL photos or just the primary one.
   - Recommendation: Load all photos for the entry, display as horizontal scroll if multiple. The query already works without LIMIT 1.

3. **Enriching re-identification results through KG**
   - What we know: geminiNanoService.identify() returns dish names + ingredient names + weights. These need KG lookup for nutrition.
   - What's unclear: Whether to reuse the full VLM pipeline (vlmPipeline.ts) or just the KG enrichment step.
   - Recommendation: Reuse the KG enrichment logic from the scan pipeline. The VLM pipeline does YOLO stuff we don't need -- extract just the KG enrichment into a reusable function.
