# Phase 09.1: Dark Mode Theme — Research

**Researched:** 2026-03-24
**Domain:** React Native theming, color system architecture, system preference detection
**Confidence:** HIGH

## Summary

This phase centralizes ~967 hardcoded hex color references across 49 files into a semantic token system, then provides light/dark palettes with a three-state toggle (System/Light/Dark). The codebase already uses a consistent Tailwind-esque gray scale (#111827 through #F9FAFB) and a small set of accent colors, making the mapping to semantic tokens straightforward. No new dependencies are needed — React Native's `useColorScheme()`, React Context, and the existing Zustand preferences store provide all necessary infrastructure.

The main risk is not technical complexity but migration scope: 49 files must be touched, and every hardcoded color must be replaced with a semantic token reference. The migration is mechanical but error-prone if done carelessly. A systematic approach (define tokens first, migrate by file, verify visually) is essential.

**Primary recommendation:** Build the theme infrastructure (colors.ts, ThemeProvider, useTheme hook) first in isolation, then migrate files in batches grouped by navigation area. Use TypeScript's type system to enforce that all color values come from the theme object.

### Pattern 2: ThemeProvider with System Detection
**What:** React Context that combines user preference with system color scheme
**When to use:** Wraps entire app at root

```typescript
// src/theme/ThemeProvider.tsx
import React, { createContext, useContext, useMemo } from 'react';
import { useColorScheme } from 'react-native';
import { usePreferencesStore } from '../store/usePreferencesStore';
import { lightColors, darkColors, type ThemeColors } from './colors';

interface ThemeContextValue {
  colors: ThemeColors;
  isDark: boolean;
}

const ThemeContext = createContext<ThemeContextValue>({
  colors: lightColors,
  isDark: false,
});

export function ThemeProvider({ children }: { children: React.ReactNode }) {
  const systemScheme = useColorScheme();
  const themePreference = usePreferencesStore((s) => s.themePreference);

  const isDark = useMemo(() => {
    if (themePreference === 'system') return systemScheme === 'dark';
    return themePreference === 'dark';
  }, [themePreference, systemScheme]);

  const value = useMemo(() => ({
    colors: isDark ? darkColors : lightColors,
    isDark,
  }), [isDark]);

  return (
    <ThemeContext.Provider value={value}>
      {children}
    </ThemeContext.Provider>
  );
}

export function useTheme(): ThemeContextValue {
  return useContext(ThemeContext);
}
```

### Pattern 3: Dynamic Styles in Components
**What:** Replace static StyleSheet.create with styles that consume theme colors
**When to use:** Every component that references colors

```typescript
// Option A: Styles factory (recommended for complex components)
function createStyles(colors: ThemeColors) {
  return StyleSheet.create({
    container: { flex: 1, backgroundColor: colors.background.primary },
    title: { color: colors.text.primary, fontSize: 18, fontWeight: '700' },
    card: { backgroundColor: colors.background.elevated, borderColor: colors.border.subtle },
  });
}

function MyScreen() {
  const { colors } = useTheme();
  const styles = useMemo(() => createStyles(colors), [colors]);
  // ...
}

// Option B: Inline styles (for simple components with few color refs)
function SimpleComponent() {
  const { colors } = useTheme();
  return <Text style={{ color: colors.text.primary }}>Hello</Text>;
}
```

### Pattern 4: React Navigation Theme Integration
**What:** Map our semantic tokens to React Navigation's theme shape
**When to use:** NavigationContainer wrapping

```typescript
// src/theme/navigation.ts
import { Theme } from '@react-navigation/native';
import { lightColors, darkColors, type ThemeColors } from './colors';

function buildNavTheme(colors: ThemeColors, isDark: boolean): Theme {
  return {
    dark: isDark,
    colors: {
      primary: colors.accent.green,
      background: colors.background.primary,
      card: colors.background.elevated,
      text: colors.text.primary,
      border: colors.border.subtle,
      notification: colors.accent.red,
    },
    fonts: {
      regular: { fontFamily: 'System', fontWeight: '400' },
      medium: { fontFamily: 'System', fontWeight: '500' },
      bold: { fontFamily: 'System', fontWeight: '700' },
      heavy: { fontFamily: 'System', fontWeight: '900' },
    },
  };
}

export const lightNavTheme = buildNavTheme(lightColors, false);
export const darkNavTheme = buildNavTheme(darkColors, true);
```

### Pattern 5: Preference Store Migration
**What:** Migrate `darkMode: boolean` to `themePreference: 'system' | 'light' | 'dark'`
**When to use:** Store definition update

```typescript
// In usePreferencesStore.ts persist config:
{
  name: 'user-preferences',
  storage: createJSONStorage(() => AsyncStorage),
  // Migration: darkMode boolean -> themePreference string
  version: 1,
  migrate: (persistedState: any, version: number) => {
    if (version === 0) {
      // Old darkMode: true -> 'dark', false -> 'system' (not 'light', to respect system default)
      const state = persistedState as any;
      state.themePreference = state.darkMode ? 'dark' : 'system';
      delete state.darkMode;
    }
    return persistedState;
  },
}
```

### Anti-Patterns to Avoid
- **Wrapping useTheme in every StyleSheet.create call without memoization:** Creates new StyleSheet objects on every render. Always `useMemo` the styles factory result keyed on `colors`.
- **Using `Platform.select` for theme colors:** Theme is cross-platform; use the semantic token system, not platform branching.
- **Hardcoding rgba overlays differently per theme:** Keep overlay colors consistent (`rgba(0,0,0,0.5)`) as they work on both light and dark backgrounds. Only theme solid backgrounds.
- **Conditional color logic in components:** All conditional logic belongs in the palette definitions, not scattered across components. Components should use `colors.X` unconditionally.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| System theme detection | Manual Appearance API listener | `useColorScheme()` from react-native | Built-in hook, handles listener lifecycle, returns reactive value |
| Navigation theming | Manual header/tab bar color overrides | React Navigation `theme` prop | Themes headers, tab bars, background, text in one place |
| Bottom sheet theming | Custom overlay/backdrop colors | `@gorhom/bottom-sheet` `backgroundStyle` + `handleIndicatorStyle` | Already supports these props, used in 4 existing sheets |
| Persisted preference with migration | Manual AsyncStorage read/write/migrate | Zustand persist `version` + `migrate` | Handles versioned migration, already the store pattern |

**Key insight:** The entire dark mode infrastructure is achievable with zero new dependencies. React Native, React Navigation, and the existing Zustand + bottom sheet stack provide every needed primitive.

## Common Pitfalls

### Pitfall 1: Missed Hardcoded Colors
**What goes wrong:** After migration, a few screens still show white backgrounds or dark text in dark mode because a hex value was missed.
**Why it happens:** 967 color references across 49 files; grep-and-replace misses colors in template literals, computed styles, or non-obvious locations.
**How to avoid:** After migration, search for any remaining hex patterns: `grep -rn "#[0-9A-Fa-f]\{3,8\}" src/ --include="*.tsx" --include="*.ts"`. Only `rgba()` overlays and the palette definition file should remain.
**Warning signs:** Visual testing in dark mode shows jarring white rectangles or invisible text.

### Pitfall 2: Forgetting StatusBar Style
**What goes wrong:** Dark mode renders but the system status bar (clock, battery) stays dark-on-transparent, becoming invisible on dark backgrounds.
**Why it happens:** `<StatusBar style="auto" />` in App.tsx needs to respond to the resolved theme, not just the system setting.
**How to avoid:** Pass `style={isDark ? 'light' : 'dark'}` to `<StatusBar>` from ThemeProvider context.

### Pitfall 3: StyleSheet Re-creation on Every Render
**What goes wrong:** Components using `StyleSheet.create(...)` inside render without memoization cause GC pressure and jank.
**Why it happens:** Dynamic styles need the colors object, so the old pattern of module-level StyleSheet.create breaks.
**How to avoid:** Use `useMemo(() => createStyles(colors), [colors])`. Since theme changes are rare (user toggle or system change), the memo cache is almost always hit.

### Pitfall 4: Zustand Persist Migration Not Versioned
**What goes wrong:** Existing users' `darkMode: boolean` persists in AsyncStorage and the new `themePreference` field is undefined.
**Why it happens:** Without a `version` + `migrate` config, Zustand persist just merges old state shape.
**How to avoid:** Add `version: 1` and a `migrate` function that converts `darkMode: true` to `themePreference: 'dark'` and `darkMode: false` to `themePreference: 'system'`.

### Pitfall 5: Accent Tint Colors Not Adapted for Dark
**What goes wrong:** Light accent tints (#F0FDF4 green background, #EFF6FF blue background) look washed out or invisible on dark surfaces.
**Why it happens:** Tint colors are designed for light backgrounds; they need dark-adapted variants.
**How to avoid:** Define separate dark tint values with lower opacity or darker base. E.g., light green tint #F0FDF4 -> dark green tint: something like `rgba(22, 163, 74, 0.15)` or a pre-computed dark value like #0D2818.

### Pitfall 6: React Navigation Theme fonts Property
**What goes wrong:** TypeScript error when building navigation theme without `fonts` property.
**Why it happens:** React Navigation v7 `Theme` type requires a `fonts` property (added in v7), unlike v6.
**How to avoid:** Include the `fonts` object in the nav theme (see Pattern 4 above). Use system fonts with standard weights.

### Three-State Toggle UI (Profile Screen)
```typescript
// In ProfileScreen, near existing UX mode setting
const THEME_OPTIONS = [
  { value: 'system', label: 'System', icon: 'phone-portrait-outline' },
  { value: 'light', label: 'Light', icon: 'sunny-outline' },
  { value: 'dark', label: 'Dark', icon: 'moon-outline' },
] as const;

function ThemeToggle() {
  const { colors } = useTheme();
  const themePreference = usePreferencesStore((s) => s.themePreference);
  const setThemePreference = usePreferencesStore((s) => s.setThemePreference);

  return (
    <View style={{ flexDirection: 'row', gap: 8 }}>
      {THEME_OPTIONS.map((opt) => (
        <Pressable
          key={opt.value}
          onPress={() => setThemePreference(opt.value)}
          style={{
            flex: 1,
            paddingVertical: 10,
            borderRadius: 8,
            alignItems: 'center',
            backgroundColor: themePreference === opt.value
              ? colors.accent.green
              : colors.background.surface,
          }}
        >
          <Ionicons
            name={opt.icon}
            size={20}
            color={themePreference === opt.value ? '#FFFFFF' : colors.text.secondary}
          />
          <Text style={{
            color: themePreference === opt.value ? '#FFFFFF' : colors.text.primary,
            fontSize: 12, marginTop: 4,
          }}>
            {opt.label}
          </Text>
        </Pressable>
      ))}
    </View>
  );
}
```

## Open Questions

1. **Accent tint dark variants**
   - What we know: Light tint backgrounds (#F0FDF4, #EFF6FF, etc.) need dark alternatives
   - What's unclear: Exact hex values for dark tint backgrounds
   - Recommendation: Use low-opacity accent colors (e.g., `rgba(22, 163, 74, 0.12)` for green tint) or pre-compute hex values: #0F2E1A (dark green tint), #172033 (dark blue tint), #1A1528 (dark purple tint). Let the implementer choose pre-computed hex for consistency with the plain-object palette approach (D-02).

2. **Shadow colors in dark mode**
   - What we know: `shadowColor: '#000'` with opacity works on light backgrounds
   - What's unclear: Whether shadows are visible/useful on dark backgrounds
   - Recommendation: Shadows are less visible on dark backgrounds. Consider increasing elevation/shadow opacity in dark mode, or using subtle border instead. This is a polish detail, not blocking.
